# Hermes Agent 插件使用教程

Hermes Agent 开箱即带 70+ 内置工具与一整套自进化技能体系，但每个团队总有"只有我们才用得到"的私有能力：某个自研 CLI 的封装脚本、一套团队统一的工作流提示词、一组约定的模型与工具配置。如果每次换机器、加人都要手工重搭一遍，体验会迅速劣化。插件的价值正在于此：**把工具、技能、配置打包成一个可安装、可分发、可共享的单元**，一条命令装进任意一台 Hermes。

本章讲清楚插件与技能的分工、插件能装什么、怎么安装与管理，以及团队如何共享插件包，让你从"一个人折腾配置"走向"一套能力团队复用"。

## 一、插件核心概念

### 1.1 插件与技能的区别

![插件打包扩展能力](/images/hermes/plugins/01-plugin-extend.png)

这是最容易混淆的一组概念，先一句话区分：

| 维度 | 插件（Plugin） | 技能（Skill） |
| --- | --- | --- |
| 本质 | 可安装、可分发的能力单元 | 可复用的工作流指令 |
| 形态 | 打包工具 / 技能 / 配置 | SKILL.md（"怎么做"的步骤） |
| 目的 | 扩展 Hermes 能力边界 | 沉淀 Agent 的工作经验 |
| 分发 | 可安装包，可团队共享 | 存于 `~/.hermes/skills/`，可导出 |
| 类比 | 应用的"安装包" | 应用的"操作手册" |

技能是 Hermes 自进化体系的核心——Agent 完成任务后把"怎么做"沉淀成程序性记忆（SKILL.md，兼容 agentskills.io 开放标准）；而插件是**更偏向"安装的分发单元"**，它可以包含一个或多个技能，也可以包含工具、配置，把一整套能力装进目标实例。**一个插件内部往往就封装着技能**——两者不是二选一，而是"沉淀"与"分发"的关系。

### 1.2 为什么要用插件

- **能力可携带**：技能、工具、配置打包成一个单元，换机器、开新 profile 也能一键装回来。
- **团队可共享**：统一封装后分发，避免"口头对齐 + 每人手搓"。
- **职责清晰**：与"临时加一条配置"相比，插件是声明式、可管理的实体，装、禁、卸都有迹可循。

## 二、插件能做什么

插件本质上是一个"能力集装箱"，通常打包三类内容：

### 2.1 打包工具

把团队自研的脚本、命令、外部工具接入方式封装进插件，安装后即可在会话中作为工具调用。典型例子：内部构建工具、部署脚本、私域知识库检索命令。

### 2.2 打包技能

一个领域通常需要一组技能配合：调研、分析、产出、复盘。把这些技能按主题打包进插件，安装即获得整套工作流，而不是一个个手动复制 SKILL.md 文件。

### 2.3 打包配置

把模型、提供商、工具集、甚至 SOUL.md 风格等约定写入插件配置，随装随用。这让"团队统一 Agent 行为基线"成为可能——新成员装上插件，行为和团队老成员一致。

| 打包内容 | 封装对象 | 安装后的效果 |
| --- | --- | --- |
| 工具 | 脚本 / CLI / 外部工具接入 | 会话中可直接调用 |
| 技能 | 一组 SKILL.md | 获得整套领域工作流 |
| 配置 | config.yaml 片段 / 行为约定 | Agent 行为对齐团队基线 |

::: tip 类比理解
插件像软件领域的"安装包"：它把程序、依赖、配置一起交付，用户装完即用；技能则像安装包内置的"帮助文档"，告诉 Agent 具体怎么干。
:::

## 三、安装与使用插件

### 3.1 安装流程

![插件安装流程](/images/hermes/plugins/02-plugin-install.png)

安装分三步：查看可用插件 → 安装 → 验证生效。

```bash
# 1) 查看可用的插件列表 / 搜索插件
hermes plugins list

# 2) 安装指定插件（<plugin-name> 以实际插件名称为准）
hermes plugins install <plugin-name>

# 3) 验证已安装
hermes plugins list
```

安装完成后，插件封装的工具 / 技能 / 配置会自动并入当前 Agent 实例；随后可用 `hermes tools` 确认相关工具集、`/skills` 确认相关技能已就位。

::: tip 安装会改变实例行为
插件安装后会修改你的 Agent 配置（工具、技能、行为基线），所以装完后应在**新会话**中验证效果，避免在重要的进行中会话里突然引入行为变化。
:::

### 3.2 使用插件能力

安装后不需要额外"启动"插件——其暴露的工具、技能直接可用，在会话里按普通工具、技能的方式调用即可。若插件带来了新配置，通常从下一个会话开始生效。

## 四、管理与禁用

插件是可管理的实体，与 cron、profile 一样拥有独立的管理命令：

| 命令 | 作用 |
| --- | --- |
| `hermes plugins list` | 查看已安装插件 |
| `hermes plugins install <name>` | 安装插件 |
| `hermes plugins update` | 更新插件 |
| `hermes plugins disable <name>` | 临时禁用插件（保留安装记录） |
| `hermes plugins uninstall <name>` | 卸载插件 |

::: warning 命令名以官方文档为准
本节子命令命名为符合 Hermes 命名习惯的示例，具体子命令、参数与插件来源，请以官方文档及 `hermes plugins --help` 输出为准。
:::

禁用一个插件后，其封装的工具 / 技能 / 配置立即停止生效，但安装记录仍在，随时可重新启用。这个特性非常适合做 A/B 验证："装了插件之后，Agent 的产出到底有没有变好"——用 `disable` 临时关掉对比即可。

## 五、实战案例：团队共享插件包

场景：一个 5 人小团队统一使用 Hermes 做周报、代码 review 摘要与部署，希望"任何人装上就能用同一套工作流"。

1. **制作插件包**：把团队的周报技能、review 提示词、内部工具封装成插件（包含一组 SKILL.md + 工具 + 约定配置）。
2. **发布到内部源**：把插件发布到团队可访问的源（私有仓库或内部 registry）。
3. **成员安装**：每人执行 `hermes plugins install <团队插件>`，一次性获得整套能力。
4. **统一基线**：新成员入职只需"装插件 + 登录提供商"，即可获得与团队一致的 Agent 行为，不再手工对齐。

团队插件包是"Agent 团队化"的低成本入口：它把隐性经验变成**可安装的显性资产**，谁装谁有、谁装都一样。

::: tip 与 Profile 的分工
如果你需要"不同角色、不同基线"的隔离实例，用 Profiles（`hermes profile create --clone` 复制技能与配置）更合适；插件更偏"能力分发"，两者可叠加使用。
:::

## 六、最佳实践与常见问题

### 6.1 最佳实践

1. **插件按"领域"而非"单点"打包**：一个领域一套插件，避免碎片化插件过多、难管理。
2. **配置类内容保持最小化**：插件只放"团队统一基线"，个人偏好留在个人配置，避免装插件顺带覆盖别人的个性化设置。
3. **先禁用再卸载**：不确定是否还需要时，先 `disable` 观察一段时间，确认无影响再 `uninstall`。
4. **先沉淀、后分发**：日常先让 Hermes 自进化生成技能，验证成熟后再收编进团队插件分发，形成闭环。

### 6.2 常见问题排查

| 问题 | 排查步骤 |
| --- | --- |
| 安装后能力没出现 | 确认安装的是正确名称的插件；用 `hermes tools` / `/skills` 核对是否生效；重开新会话再试 |
| 插件与现有配置冲突 | 检查插件打包的配置是否覆盖了你的个人设置；优先把插件配置限制在团队基线内 |
| 更新后行为异常 | `hermes plugins disable <name>` 临时禁用，比对是否由插件引起；必要时回退到旧版本 |
| 团队分发失败 | 确认内部源的权限与版本；检查插件是否引用缺失的依赖（工具 / 技能路径） |

## 总结

插件是 Hermes 的"能力安装包"：它把工具、技能、配置打包成可安装、可分发、可管理的单元，与"沉淀工作流"的技能互补——技能负责"怎么做的步骤"，插件负责"怎么装进来的分发"。对个人，它是换机器、开新 profile 时的一键还原；对团队，它是经验显性化、基线统一化的低成本入口。记住"装完重开会话验证、冲突先禁用再卸载"这两条，就能把插件用得又稳又省心。
