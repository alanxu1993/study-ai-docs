# Hermes 代理上下文使用教程：从核心概念到最佳实践

> 来源：[Hermes Agent 官方文档](https://hermes-agent.nousresearch.com/docs/zh-Hans/) · [GitHub: NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)

两个 Hermes 装上同一个模型，一个像"有个性的老员工"，一个像"没记性的临时工"，差别往往不在模型，而在**上下文（Context）怎么配**。上下文是 Agent 思考的"工作台"——它每次回答前眼前摊开的全部材料。工作台整洁、信息对口，输出质量自然高；工作台堆满无关信息、互相矛盾，再强的模型也会跑偏。本章从核心概念讲起，直到最佳实践，帮你把这个"工作台"收拾得明明白白。

## 一、上下文核心概念

### 1.1 什么是上下文（一句话懂）

**上下文**是 Agent 处理当前请求时使用的全部输入信息，大致包括四部分：

| 组成部分 | 内容 | 来源 |
| --- | --- | --- |
| 系统提示（system prompt） | 模型行为的基础设定 | 框架内置 |
| 个性与人格 | SOUL.md 定义的默认风格 | 用户配置 |
| 项目上下文 | 项目级约定文件（类似 AGENTS.md / CLAUDE.md） | 项目配置 |
| 会话历史 + 记忆 | 本次对话的过往消息、长期记忆 | 运行时生成 |

类比理解：上下文就像你给一位新人**入职时摆在桌上的材料**——岗位手册（system prompt）、公司文化（SOUL.md）、项目规范（上下文文件）、工作笔记（记忆）和之前的会议记录（会话历史）。它决定了这位"新人"以什么姿态、依据什么信息干活。

![上下文组成结构](/images/hermes/context/01-context-composition.png)

### 1.2 上下文窗口限制：至少 64K

模型的上下文窗口是"工作台"的物理边界。Hermes 有明确要求：**模型需至少支持 64K tokens 上下文**——因为多步工具调用需要充足的工作记忆，窗口太小，Agent 会"忘记"前面几步做了什么。

- 本地运行时，需设置 `--ctx-size 65536`（约 64K）；
- 会话中可用 `/model <name>` 切换模型，切换后窗口大小随模型而定。

::: warning 超窗口会"失忆"
一旦输入总量超过上下文窗口，最早的内容会被截断丢弃，Agent 可能忘记最开始的要求、甚至忘记它正在进行的任务。多步任务中这是最常见的"中途跑偏"原因之一。
:::

### 1.3 上下文 vs 记忆：别搞混

上下文是**当次会话的动态材料**，记忆是**跨会话的长期沉淀**。记忆在每次对话开始时会**注入**到上下文中，成为上下文的一部分。可以理解为：记忆是"从笔记本誊写过来的要点"，上下文是"此刻桌上全部的纸"。内容拼装、注入的取舍，正是本章要管理的东西。

## 二、SOUL.md：定义 Hermes 的人格

### 2.1 什么是 SOUL.md

**SOUL.md** 是 Hermes 的**全局个性文件**，定义它默认的风格、语气、行为偏好。它位于 `~/.hermes/SOUL.md`（原生 Windows 在 `%LOCALAPPDATA%\hermes\SOUL.md`），**每个 profile 可以有独立的 SOUL.md**——这意味着一台机器上的多个 Agent（如"写代码的 coder"和"写文案的 writer"）可以拥有不同人格。

类比理解：SOUL.md 是给 Agent 写的**人设卡**。没写就是"默认路人"；写好就是"你专属的搭档"。

### 2.2 SOUL.md 书写示例

SOUL.md 是 Markdown 文件，写法自由，但建议清晰、具体、可执行。下面是一份可复制修改的示例：

```markdown
# 我的 Hermes 人格

## 身份
你是一位资深全栈工程师助手，重视代码质量与可维护性。

## 沟通风格
- 中文回复，简洁直接，不废话；
- 先给结论，再给理由；复杂问题用列表拆解；
- 主动指出潜在风险，而不是只报喜。

## 工作偏好
- 命名：Python 用 snake_case，前端组件用 PascalCase；
- 改动代码前先说明计划，涉及删除/破坏性操作必须征询确认；
- 优先给出可直接运行的完整示例，而不是只说思路。

## 边界
- 不做违法、危险操作；
- 不确定的事实明确说"需要核实"，不编造。
```

### 2.3 书写技巧

- **写"偏好吗？不，写"标准"**：与其写"要有好的命名"，不如写"Python 用 snake_case"这类可判定的规则；
- **行为优先于形容词**："简洁"很模糊，"先给结论再给理由"才是 Agent 能照做的；
- **别与项目上下文冲突**：SOUL.md 是全局人格，项目上下文是项目特例，冲突时要在某一层写明优先级（见第四章）。

::: tip profile 级独立人格
在 Profiles 教程里你学过 `hermes profile create coder --clone` 之类命令。每个 profile 独立 `SOUL.md`，意味着你可以把"审慎的代码审查员"和"快速的原型手"分别配置成两个 Agent，同一台机器、两套人格，互不干扰。
:::

## 三、项目上下文文件：给每个项目定规矩

### 3.1 什么是项目上下文文件

**项目上下文文件**是作用域**项目**的上下文，影响该项目的每次对话——与 Claude Code 的 CLAUDE.md、Codex 的 AGENTS.md 思路一致。放什么？项目的技术栈、目录约定、常用命令、团队成员习惯、部署流程。它的价值在于：**跟着项目走**，Clone 到哪、约定带到哪。

| 对比项 | SOUL.md | 项目上下文文件 |
| --- | --- | --- |
| 作用域 | 全局（或 profile） | 单个项目 |
| 管什么 | 人格、风格、默认行为 | 项目事实、约定、命令 |
| 典型位置 | `~/.hermes/SOUL.md` | 项目根目录下的约定文件 |
| 类比 | 公司文化手册 | 具体项目的操作规程 |

### 3.2 示例

以 VitePress 文档项目为例：

```markdown
# 项目：study-ai-docs

## 技术栈
- VitePress 静态文档站，内容在 docs/ 下；
- 中文写作，章节编号用"一、二、三"。

## 约定
- 命令示例必须可直接复制，配置项与实际工具一致；
- 插图放 docs/public/images/<section>/<chapter>/NN-xxx.png；
- 不编造配置项，不确定处写"以官方文档为准"。

## 常用命令
- 本地预览：pnpm docs:dev
- 构建：pnpm docs:build
```

这些内容每次在该项目下对话都会进入上下文，Agent 无需追问就知道怎么写文档、图片放哪。

::: warning 项目上下文别塞"会话内容"
项目上下文文件是**长期约定**，不是工作日志。把临时任务、一次性问答写进去，会持续占用宝贵的上下文窗口，而且污染每个会话。临时信息留在会话历史里即可。
:::

## 四、上下文如何组合：Agent 的完整视角

一次对话中，Hermes 的"工作台"是这样拼装起来的：

```
上下文 = 系统提示（基础设定）
      + SOUL.md（人格/风格）
      + 项目上下文文件（项目约定）
      + 记忆（跨会话事实，MEMORY.md / USER.md）
      + 会话历史（本次对话往来自动注入）
```

### 4.1 各层的优先级与覆盖

| 层 | 优先级直觉 | 冲突时倾向 |
| --- | --- | --- |
| 系统提示 | 框架级基础 | 框架兜底，一般不改 |
| 会话内直接指令 | 最高 | 用户当场说的话最优先 |
| 项目上下文 | 高 | 覆盖全局默认，项目特例以它为准 |
| SOUL.md | 中 | 提供默认，但可被项目/会话覆盖 |
| 记忆 | 中 | 提供事实背景，错误记忆需清理 |

一个典型场景：SOUL.md 说"回复简洁"，但项目上下文要求"文档示例必须完整可复制"——后者是项目的硬性约定，实际行为应偏向满足项目要求。**冲突无法消除时，在上下文里写明优先级**，Agent 才有一致的行为标准。

### 4.2 为什么"组合"很重要

单看每一层都很简单，真正决定输出质量的是**组合后的视角是否自洽**：人格统一（SOUL）、事实正确（记忆）、规范对口（项目上下文）、任务清晰（会话）。四者对齐时，Agent 的输出既有风格又有依据；任何一层跑偏，都会反映在结果里。

## 五、上下文管理最佳实践

1. **精简是王道**：上下文窗口有限，每一条上下文都要"值回票价"。无关的信息越少，模型注意力越集中在关键处；
2. **避免冲突**：SOUL.md 与项目上下文尽量各管一摊，重叠处写明覆盖关系，杜绝同一件事两种说法；
3. **按需注入**：记忆只留长期事实，项目上下文只留项目级约定，临时内容留在会话里，别持续占用窗口；
4. **SOUL 少而精**：人格写"可判定的标准"而非形容词，一页能说完最好；
5. **定期体检**：发现 Agent 行为漂移（风格变、忘约定），先查三层——SOUL.md 是否被覆盖、项目上下文是否过时、记忆是否被污染。

## 六、常见问题

| 问题 | 排查步骤 |
| --- | --- |
| 上下文溢出（Agent"失忆"、任务跑偏） | ① 确认模型支持 ≥64K 上下文，本地运行时加 `--ctx-size 65536`；② 精简项目上下文与记忆，删掉低价值内容；③ 长任务分段执行，避免单会话过载 |
| 优先级冲突（行为飘忽） | ① 检查 SOUL.md 与项目上下文是否说法矛盾；② 在冲突处显式写明"以某层为准"；③ 用 `/model` 切换模型后重测行为 |
| SOUL.md 不生效 | ① 确认文件路径正确（profile 是否独立 SOUL）；② 检查是否被项目上下文覆盖；③ 修改后新会话才完整生效 |
| 项目上下文没被加载 | ① 确认文件在项目根目录且命名正确；② 确认当前工作目录在该项目下；③ 查看 `hermes config` 中相关路径设置 |
| 切换 profile 后人格变了 | 正常：每个 profile 独立 SOUL.md，确认你激活的是预期 profile（提示符会显示 `coder ❯` 之类） |

## 总结

上下文是 Hermes 思考的"工作台"，由系统提示、SOUL.md、项目上下文、记忆、会话历史五层组合而成。用好它的三板斧：**SOUL.md 写人格标准、项目上下文定项目规矩、记忆和会话按需注入**，同时守住 64K 窗口的物理边界、避免层级冲突。配置得当，同样的模型会输出完全不同的质量——这就是"工具"与"搭档"的分水岭。下一章，我们将看到 Hermes 最独特的能力：让 Agent 自己写技能、沉淀"怎么做"。
