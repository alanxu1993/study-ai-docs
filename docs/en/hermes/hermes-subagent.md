# Hermes Agent SubAgent 子代理

一个 Hermes Agent 在默认情况下是"单线程"的：调研、改代码、跑测试，它只能一步一步来。当你丢给它一个体量很大的任务——比如"调研 5 个方向并出一份对比报告"——它会把这些步骤串起来执行，一个方向一个方向地做完，耗时随任务量线性增长，主上下文也被撑得越来越大，前期的调研细节还可能在长会话中被"挤出"上下文窗口。

SubAgent（子代理）正是为解决这个问题设计的：主代理可以把彼此独立的子任务委派给子代理，让它们**并行执行、互不干扰**，最后把结果收回来统一汇总。它把一个"超长串行任务"改造成"短并行任务"，是 Hermes 多 Agent 协作与并行 fan-out 的核心能力。这一章讲清楚子代理是什么、怎么用、什么时候用，以及最容易被忽略的坑。

## 一、SubAgent 核心概念

### 1.1 一句话理解 SubAgent

子代理是主代理通过 **delegate_task** 工具派生出来的一个"独立工作单元"：主代理把一段明确的任务说明交给它，它拿着自己的上下文与工具去执行，完成后把结构化结果返回给主代理。整个过程对使用者是透明的——你看到的仍是主代理的对话，但脏活累活已经被拆分到了后台并行处理。

> 类比理解：子代理像团队里的"外包小组"。项目经理（主代理）把任务边界写清楚后发包，小组做完交回成果；项目经理不关心小组内部怎么折腾，只验收结果。

### 1.2 delegate_task 委派工具

![主代理委派子代理](/images/hermes/subagent/01-delegate.png)

delegate_task 属于 `delegation`（委派）工具集。主代理在推理过程中，遇到适合拆分的任务时，会自动判断并调用它；你在对话里给主代理下指令时，也可以明确要求它委派。一次委派通常包含三个要素：

| 要素 | 作用 | 举例 |
| --- | --- | --- |
| 任务说明（prompt） | 告诉子代理做什么、产出什么 | "调研 X 产品的定价策略，输出对比表" |
| 任务边界 | 限制子代理的活动范围 | "只读仓库 docs/ 目录，不修改任何文件" |
| 结果要求 | 约定返回格式 | "返回 markdown 列表 + 结论摘要" |

委派工具位于 `delegation` 工具集，可先通过 `hermes tools` 确认该工具集处于启用状态（见第三章实操）。

### 1.3 任务边界：隔离与专注

每个子代理运行在**独立的上下文**中，不会把主代理的大段历史复制走，也不会把主代理的记忆、会话状态随意带进带出。这带来两个直接好处：

- **上下文干净**：子代理只装载完成本任务所需的信息，避免"信息过载"导致前期内容被挤出窗口。
- **错误隔离**：子代理如果在一连串操作中把上下文搞乱，损失被限制在它自己范围内，不会污染主代理的工作记忆。

::: warning 上下文隔离 ≠ 文件系统隔离
子代理与主代理共享文件系统权限，Profile 也不会给子代理单独做沙箱。委派时务必把"允许改什么、禁止碰什么"写清楚，否则子代理有权限动的文件它都可能动。
:::

### 1.4 结果回收

子代理完成工作后，把结果作为结构化返回值交回主代理，由主代理负责汇总、交叉验证、续写。也就是说，**子代理负责"做"，主代理负责"验收和整合"**。回收回来的结果会进入主代理的上下文，成为后续决策的依据；正因为如此，任务说明里的"结果要求"越具体，回收后的整合成本越低。

## 二、使用场景

![子代理并行执行](/images/hermes/subagent/02-parallel.png)

子代理最有价值的地方在于并行与拆解。以下三类场景最值得用。

### 2.1 并行调研

同一个主题下多个独立方向需要同时摸底时，串行逐个查太慢。把每个方向委派给一个子代理，让它们并行搜索网页、读文档、对比方案，最后主代理汇总成一份统一格式的报告。**耗时从"所有方向之和"降为"最慢的那个方向"**，这是 fan-out 最典型的收益。

### 2.2 多任务拆解

一个大需求里包含若干彼此独立、目标明确的子任务（例如"写 README、补测试、跑 lint、出变更日志"），可以一次拆给多个子代理分头做，避免主代理一件事一件事地排队执行。

### 2.3 长任务分块

一个超长任务（例如梳理 50 个文件的代码库并逐文件总结）如果全部塞进主上下文，会迅速逼近模型上下文上限——Hermes 要求模型至少支持 64K tokens 上下文，但上下文空间也不该被一次调研浪费掉。把文件分批交给子代理总结，每批产出一个浓缩摘要，主代理只负责拼接摘要，**用子代理的上下文，换取主代理的续航能力**。

::: tip 判断标准
一个任务"适不适合拆"看两件事：① 与其他部分是否**低耦合**（子任务间不需要频繁交换信息）；② 目标是否**单一明确**（子代理能一次说清要做什么）。同时满足再拆，否则硬拆只会让协调成本超过收益。
:::

## 三、实操：会话中触发委派

### 3.1 自然语言触发

在 TUI 会话里，你不必手动调用工具——直接对主代理说清楚就行。例如：

> "下面三个方向各开一个子代理并行调研：A 定价、B 竞品功能、C 社区口碑，每个给我 500 字结论，最后你汇总成一张对比表。"

主代理会把这句话解析为多次 delegate_task 调用：为 A、B、C 各派生一个子代理并行执行，回收结果后汇总输出。

### 3.2 控制子代理数量

并行不是无限并行。你可以通过措辞限制并发数，例如"最多同时跑 3 个子代理"；Hermes 会结合任务依赖关系决定 fan-out 规模。一般建议**并发数控制在 3～5 个**，尤其当子代理需要操作浏览器、执行代码等重工具时，过高的并发会引发工具竞争与上下文争抢。

### 3.3 确保委派工具可用

委派能力属于工具集，先确认已启用：

```bash
hermes tools   # 查看 / 配置启用的工具集，确认 delegation（委派）处于启用状态
```

如果工具被禁用，主代理将无法派生子代理，任务会被自己串行扛下，表现为"没有并行效果"。

## 四、与 cron 后台任务的配合

cron 定时任务在**新会话**中运行 agent 任务，且 prompt 必须**自包含**——这正好和子代理"一个任务、一份明确说明"的形态互补。两者组合起来能构造"无人值守的并行管线"：

| 组合方式 | 做法 | 效果 |
| --- | --- | --- |
| 定时触发 + 并行拆解 | 在 cron 的 prompt 里写"用子代理并行调研…再汇总" | 每天固定时间自动跑一轮多路调研 |
| cron 产出 + 结果投递 | cron 把汇总结果投递到 Telegram / email | 无人值守地收到并行任务报告 |

由于 cron 任务运行在独立的新会话里，其内部再委派子代理，等于"后台任务里再开并行任务"，彼此完全隔离、互不阻塞。需要定时自动化与并行能力完整配合时，建议先阅读 cron 章节，再回来组合使用。

## 五、与其他 Agent 的 SubAgent 对比

Codex 与 Claude Code 也提供子代理机制，思想同源，实现各有侧重：

| 维度 | Hermes SubAgent | Codex subagent | Claude Code subagent |
| --- | --- | --- | --- |
| 触发方式 | `delegate_task` 工具（会话内自动 / 自然语言） | 会话内指令派生子代理 | `/agents` 或 Agent 工具派生 |
| 上下文 | 独立上下文，与主代理隔离 | 独立上下文，隔离 | 独立上下文，隔离 |
| 并行 | 支持并行 fan-out | 支持多个并行 | 支持多个并行 |
| 结果返回 | 结构化结果回收，主代理汇总 | 子代理完成后主代理接管 | 结果返回主代理继续处理 |
| 典型定位 | 多 Agent 协作、并行调研 fan-out | 需要并行分解的编码任务 | 按需加载的专用 Agent 任务 |

三者都不是"额外多花一笔大模型调用费"的机制——子代理复用主代理的模型配置，核心价值在于**上下文隔离 + 并行 + 主代理统筹**。各工具子代理的触发方式、参数形态与限制以各自官方文档为准。

## 六、最佳实践与常见问题

### 6.1 最佳实践

1. **任务说明要自包含**：子代理没有你的完整对话历史，委派时把背景、范围、输出格式一次写清，别指望它"懂你之前的上下文"。
2. **约定返回格式**：要求"表格 / 列表 / 摘要 + 关键结论"，方便主代理回收后直接汇总，省去二次整理。
3. **控制并发规模**：3～5 个为宜；任务间存在强依赖时，优先串行或按阶段拆。
4. **把委派流程沉淀为技能**：一旦某类"拆解 → 委派 → 回收 → 汇总"的流程验证有效，可让 Hermes 沉淀为 Skill，下次一句话复用（详见技能章节）。

### 6.2 常见问题排查

![子代理结果回收](/images/hermes/subagent/03-collect-results.png)

| 问题 | 排查步骤 |
| --- | --- |
| 子代理结果丢失 / 缺失 | 检查是否明确要求"返回结果"；子代理被终止或任务被中断时结果可能未及回收——重跑该子任务；确认结果是否因上下文超限被裁剪 |
| 委派没发生，主代理自己全干了 | 任务可能被判定为"强耦合、不适合拆"；尝试更明确地指示"把 XX 拆成 N 个独立子任务并行执行" |
| 并行后结果相互矛盾 | 说明子任务之间实际存在耦合；合并范围或约定统一的数据口径后重跑 |
| 子代理操作越界（改了不该改的文件） | 记住子代理不隔离文件系统、与主代理权限相同；在任务边界里明确"只读 / 只允许改某目录"并设置命令审批 |
| 并发太多导致卡顿 | 明确限制并发数量（"最多同时 3 个"）；避免多个子代理同时跑浏览器 / 代码执行等重工具 |

## 总结

SubAgent 是 Hermes 多 Agent 协作的核心：通过 `delegate_task` 把独立任务委派给并行子代理，用独立上下文换取主代理的续航，再把结果回收汇总。它的适用信号是"低耦合 + 目标明确"，最佳搭配是"自包含的任务说明 + 约定好的返回格式 + 3～5 个并发"，并可用 cron 把整套并行管线做成无人值守。记住那句最重要的提醒——**上下文隔离 ≠ 文件系统隔离**，委派时把边界写清楚，并行就能又快又稳。
