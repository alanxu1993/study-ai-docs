# Codex Subagent 实用教程

单线程的 AI 编程助手有一个天然的瓶颈：一次只能顺着一条思路往下走。当你既想并行重构多个模块、又想同时审查两个 PR 时，主代理只能排队处理，一个长任务下来往往要等上几十分钟。Codex 的 Subagent（子代理）正是为打破这个瓶颈而生：主代理把相互独立的子任务"分派"给多个子代理并行执行，再把结果回收整合。学会用好子代理，是让 Codex 从"单线程思考"升级为"多线程团队协作"的关键一步。

## 一、Subagent 核心概念

### 1.1 什么是子代理（一句话懂）

子代理是主代理在会话内部临时创建的工作单元——主代理负责任务拆分、调度与结果整合，每个子代理持有独立的上下文窗口，并行推进自己的那份子任务。

类比理解：主代理是项目经理，子代理是手下的工程师。项目经理不会亲自把所有代码写完，而是把"你负责 API 层、你负责补测试、你负责改文档"逐一分派下去，最后再逐份验收汇总。这样无论多少子任务，整体耗时只取决于最慢的那个。

### 1.2 委派模型

子代理的运作遵循一个清晰的"委派-执行-回收"模型：

| 阶段 | 角色 | 做什么 |
| --- | --- | --- |
| 委派 | 主代理 | 把独立任务连同上下文、目标、约束拆包给子代理 |
| 执行 | 子代理 | 在独立上下文窗口中完成工具调用与代码修改 |
| 回收 | 主代理 | 汇总各子代理输出，整合冲突、继续推进 |

委派的前提是**任务相互独立**。如果两个子代理同时修改同一个文件、互相依赖对方的产物，就会产生上下文隔离带来的"信息孤岛"——这也是子代理使用中最常见的误区（详见第六章）。

### 1.3 并行执行

多个子代理默认并行运行，各自的 token 上下文、对话历史互不干扰。这带来两个直接收益：

- **吞吐量线性提升**：N 个独立任务并行，总耗时从"逐个累加"变为"约等于最慢任务耗时"。
- **上下文隔离**：一个子代理处理 20 个文件，不会把另外 20 个文件的噪声灌进主代理上下文——主代理只看到子代理返回的结论，保持轻量。

![主代理委派子代理](/images/codex/subagent/01-delegation.png)

### 1.4 结果回收

子代理完成或被中断后，主代理回收其输出。注意：**子代理的完整上下文不会回流到主代理**，主代理拿到的是结论摘要与变更结果。这意味着委派时要"把话说明白"——任务描述里包含验收标准，比事后追问"你看到了什么"更高效。

## 二、配置：[agents] 节详解

子代理的并行能力通过 `config.toml` 的 `[agents]` 节控制，可写在全局 `~/.codex/config.toml` 或项目级 `.codex/config.toml`。

### 2.1 最小配置示例

```toml
# ~/.codex/config.toml 或 .codex/config.toml
[agents]
max_threads = 6               # 并行子代理线程数，默认 6
max_depth = 1                 # 子代理嵌套深度，默认 1
job_max_runtime_seconds = 600 # 单个子代理任务的最长运行时间（秒）
```

### 2.2 关键字段详解

| 配置项 | 默认值 | 作用 | 建议 |
| --- | --- | --- | --- |
| `max_threads` | `6` | 可同时运行的子代理线程上限 | 大项目可调高，但注意 API 配额与上下文成本 |
| `max_depth` | `1` | 子代理允许的最大嵌套层数 | 绝大多数场景保持 1，避免"套娃"失控 |
| `job_max_runtime_seconds` | 无默认（以官方文档为准） | 单个子代理任务超时保护 | 长任务单独评估，防止僵尸任务占线程 |

![子代理线程与深度配置](/images/codex/subagent/03-thread-depth.png)

::: tip 为什么 max_depth 默认只有 1？
深度 1 意味着"主代理 → 子代理"一层就到头了，子代理不会再派生子代理。这保证调用树扁平、成本可控。若业务确实需要"子代理的子代理"（如子代理内部再并行扫描），再按需加深——但每加深一层，token 消耗和调度复杂度都会显著上升。
:::

::: warning 线程不是免费的
`max_threads` 调大不等于"白赚算力"。每个线程都占用模型 API 配额与上下文成本，同一时刻并发过多还会触发限流。先按默认 6 跑通，再根据实际任务量微调。
:::

## 三、多代理编排

### 3.1 并行 fan-out 模式

官方文档 `/codex/multi-agent/` 描述的并行 fan-out，是子代理最典型的编排方式：主代理把一个大任务"扇出"成多个并行子任务，各自执行后再"扇入"汇总。官方文档对子代理的完整说明以 `/codex/multi-agent/` 为准。

fan-out 适合的典型形态：

- 一个需求拆成"改前端 + 改后端 + 改文档"三个独立工作流并行推进；
- 一个大型仓库按目录切分，每个子代理负责一个子目录；
- 一次升级同时跑"静态扫描 + 单元测试 + 依赖检查"三类检查。

### 3.2 collaboration_modes 与 Plan 模式

`collaboration_modes` 特性开启后支持 **Plan 模式**——把"规划"与"执行"两个阶段分离：

| 模式 | 职责 | 适合时机 |
| --- | --- | --- |
| 常规模式 | 边规划边执行，即时反馈 | 需求明确、改动范围小 |
| Plan 模式 | 先产出完整方案，经确认后再执行 | 改动大、影响面广、需要人工确认方案 |

开启方式（特性管理命令）：

```bash
codex features enable collaboration_modes
codex features list   # 确认已生效
```

::: tip 编排口诀
小任务单代理直干，大任务 fan-out 并行，高风险任务先 Plan 再执行。三者组合能覆盖 95% 的日常场景。
:::

## 四、实用场景

### 4.1 并行代码审查

把多个待审查文件/PR 分派给不同子代理，各自输出"问题清单 + 修改建议"，主代理统一回收去重。相比逐个文件串行审查，时间可压缩到原来的 1/N，且每个子代理聚焦单个文件，审查深度更高。

### 4.2 多模块重构

重构最大的风险是"牵一发动全身"。fan-out 重构时，务必先在 Plan 模式确认模块边界与接口契约，再让子代理各自处理互不依赖的模块，最后主代理统一验证跨模块调用是否还成立。跨模块的公共接口改动，建议由主代理亲自处理，避免多子代理改出冲突。

### 4.3 测试探索

面对一个大仓库的测试覆盖盲区，可以让子代理分组探索：一组扫"无测试覆盖的核心函数"，一组扫"历史变更频繁的脆弱区域"，一组跑"现有测试的失败模式"，三份结论汇合后由主代理形成补测计划。测试探索天然可切分、无副作用，是子代理最安全的练兵场。

## 五、与 Hooks SubagentStop 事件的联动

子代理完成时会触发 `SubagentStop` Hook，这让子代理不仅能并行干活，还能自动收尾。启用方式与普通 Hook 一致（需 `codex_hooks = true` 特性，v0.124 起稳定）：

```json
{
  "hooks": {
    "SubagentStop": [
      {
        "matcher": "auto",
        "hooks": [{ "type": "command", "command": "node ./.codex/hooks/on-subagent-stop.mjs" }]
      }
    ]
  }
}
```

`SubagentStop` 事件的实用价值：

| 用途 | 示例 |
| --- | --- |
| 结果落盘 | 每个子代理完成后，立即把产出写入日志/文件 |
| 聚合通知 | 全部子代理完成后再统一触发汇总，而非逐个打断 |
| 失败告警 | 检测子代理异常退出，及时通知或自动重试 |

::: warning 读懂退出码
Stop/SubagentStop 类 Hook 返回非零退出码时，Codex 会**继续处理**，不会因此中断整个会话——这是它区别于 PreToolUse 拦截行为的关键。别把"想中断"的逻辑写在这里。
:::

## 六、最佳实践与常见问题

### 6.1 最佳实践清单

- **任务粒度要独立**：只有无共享状态的子任务才适合委派；涉及同一文件/同一接口的改动合并给一个子代理。
- **委派时写明验收标准**：子代理上下文不回流主代理，任务描述里直接给出"完成 = 测试通过 + 无回归"这类可判定的标准。
- **控制并发与深度**：先 6 线程、1 层深度跑通，再按需调整；观察 API 配额再决定是否加码。
- **高风险改动走 Plan 模式**：先方案、后执行，避免并行改出不可控的冲突。

### 6.2 常见问题排查

| 现象 | 可能原因 | 排查步骤 |
| --- | --- | --- |
| 子代理频繁超时 | `job_max_runtime_seconds` 过小或任务过大 | 检查 `[agents]` 配置；把大任务再拆小 |
| 改完的文件互相冲突 | 任务存在隐含依赖 | 改用单子代理处理有依赖的部分；先在 Plan 模式确认边界 |
| 并发过高被限流 | `max_threads` 超出 API 配额 | 调低线程数，错峰执行 |
| 子代理结果"感觉丢了信息" | 委派描述不含验收标准 | 在任务描述中写明目标、输入、输出格式 |
| 想拒绝/阻断某子任务 | 误用了 SubagentStop 拦截 | 拦截逻辑应放 PreToolUse，而非 SubagentStop |

## 七、总结

Subagent 把 Codex 从"串行执行者"升级为"并行协调者"：核心在于理解委派模型（独立任务 + 独立上下文 + 结论回收）、掌控 `[agents]` 配置（`max_threads`、`max_depth`、`job_max_runtime_seconds`）、善用 Plan 模式与 SubagentStop 完成编排闭环。它的价值不是"多干活"，而是**让该并行的并行、该串行的串行**——把时间花在真正需要主代理整合的决策点上。学会委派，是 Codex 进阶路上性价比最高的一课。
