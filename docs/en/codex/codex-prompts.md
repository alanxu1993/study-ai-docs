# Codex 提示词使用教程

提示词是你与 Codex 打交道最直接的交互界面——你输入的每一句话，都可能决定一次会话是"十分钟改完一个小功能"，还是"两个小时来回拉扯"。很多用户把 Codex 当成搜索引擎来用，丢一句"帮我优化一下代码"就等着看结果，得到的往往是笼统、低质甚至跑偏的输出。写好提示词不是玄学，而是有原理、有方法、可以沉淀复用的工程技能。

本章从 Codex 提示词的工作原理讲起，逐步给出高质量提示词的核心技巧、三种进阶模式，以及官方最推荐的一个关键习惯：把验证有效的提示词编码进 AGENTS.md，让好提示词一次写好、处处生效。文末附一个完整的重构案例和常见问题排查表。

## 一、Codex 提示词工作原理

### 1.1 提示词进入 Codex 的三条路径

很多人以为 Codex"只看到了我打的字"。实际上，模型每次生成回复时，读到的是三层内容的组合：

| 输入来源 | 谁控制 | 加载时机 | 核心作用 |
| --- | --- | --- | --- |
| 系统提示词（system prompt） | OpenAI 内置 | 每次请求 | 定义 Codex 的角色、可用工具、基本行为边界 |
| 用户提示词（user prompt） | 你 | 每次输入 | 当前任务的目标、上下文、约束与验收标准 |
| AGENTS.md 注入 | 项目维护者 | 会话启动时 | 项目级指令：仓库结构、命令、约定、完成定义 |

![提示词进入 Codex 的三条路径](/images/codex/prompts/01-prompt-paths.png)

其中 AGENTS.md 是理解 Codex 提示词体系的钥匙。它是"给 Agent 看的 README"，会话开始时会自动注入模型：全局级 `~/.codex/AGENTS.md` 每次会话都读，项目级仓库根 `AGENTS.md`、子目录级 `AGENTS.md` 按路径作用域生效且嵌套级联——越靠近当前工作目录优先级越高。也就是说，你在提示词里反复叮嘱的"测试用 pytest 跑""不要动 src/config 下的文件"，本可以只写进 AGENTS.md 一次。

### 1.2 提示词 ≠ 一句话指令

理解这三层结构，就明白了两件事：

1. **提示词是"增量"，不是"全部"**。Codex 的行为由系统提示词打底、AGENTS.md 定型、你的用户提示词定向。你写得再具体，也无法覆盖每一条规则——所以好提示词应当聚焦"本次任务特有"的信息，把可复用的约定留给 AGENTS.md。
2. **上下文是会被消耗的**。会话越长、注入内容越多，模型越容易"忘了前面的约定"。这也是为什么官方反复强调：把可复用规则放进 AGENTS.md，而不是每次在 prompt 里重复。

### 1.3 好提示词 vs 差提示词

先看一个直观对比，同样是"改支付模块"：

| 维度 | 差提示词 | 好提示词 |
| --- | --- | --- |
| 目标 | "帮我优化一下代码" | "把 `src/payments/process_order` 拆成 charge/refund/reconcile 三个函数，各司其职" |
| 约束 | 无 | "不改变对外 API 签名，错误码与日志格式保持不变" |
| 验收 | 无 | "npm test 全部通过，lint 无新增告警" |
| 上下文 | 只描述问题 | 给出文件路径、技术栈、可参考的现有模块 |

差的提示词把决策权全部外包给模型的猜测，好的提示词把目标、边界、终点一次性讲清。下面给出具体的写法方法论。

## 二、高质量提示词核心技巧

### 2.1 三要素：具体目标、约束条件、验收标准

无论任务大小，一个高质量提示词都应当包含三个要素：

- **具体目标**：动词开头，指明改什么、改成什么样。避免"优化""改善""弄一下"这类模糊动词，换成"重构为""增加""删除""迁移到"。
- **约束条件**：划清红线——不能动的接口、必须保持的兼容性、禁止使用的命令、依赖的技术栈版本。约束越明确，Codex 越不会"自由发挥"。
- **验收标准**：告诉 Codex 什么算"做完了"。可执行的验收（跑测试、lint 通过）优于描述性的验收（"质量要高"）。

对照官方 Prompting Guide 的核心要点，还可以进一步补充：

- **给出精确的代码位置**：文件路径、函数名、行号，减少模型大海捞针；
- **指明输出格式**：需要 diff、表格、JSON 还是摘要？明确格式能大幅提升结果的可用性；
- **一次聚焦一件事**：把"重构 + 加测试 + 写文档"拆成多个轮次，每轮一个明确目标，成功率远高于一股脑塞进一条 prompt；
- **提供足够背景**：技术栈、相关文件、现有约定，缺上下文时模型只能用最通用的假设。

### 2.2 一个可直接套用的通用模板

```text
背景：<这段代码/模块是什么，技术栈是什么>
目标：<具体要做成什么，动词开头，可度量>
约束：
1. <红线 1：不能改动的接口/文件>
2. <红线 2：必须保持的兼容性/格式>
验收标准：
1. <可执行验证：npm test 全绿>
2. <回归要求：现有功能不受影响>
完成后请：<列出修改的文件，并逐个说明改了什么>
```

这个模板把三要素 + Prompting Guide 要点浓缩进固定结构，实战中直接填空即可。

## 三、进阶模式

掌握基础写法后，有三个官方推荐的进阶模式，能覆盖大多数"一次搞不定"的场景。

### 3.1 模糊需求：先让 Codex 反问澄清

需求本身模糊时，别指望模型替你猜。官方 Prompting Guide 明确建议：**先让 Codex 反问问题**，澄清后再动手。在提示词开头显式声明即可：

```text
不要直接开始实现。先基于你的分析，向我提出 3-5 个关键问题，
例如：优先级是什么？需要兼容哪些平台/版本？有没有必须保持的既有接口？
等我逐一回答并确认后，再给出实施方案。
```

这一招成本极低、收益极高：一次澄清能省掉一整轮"做出来 → 方向错了 → 重做"的循环。

### 3.2 PLANS.md 多步规划模板

对于跨多文件、多阶段的长期任务，官方推荐"先规划、后执行"的工作流：**先让 Codex 写出一份 PLANS.md 规划，按计划执行，再逐项检查**。一个可直接套用的模板：

```markdown
# PLANS.md

## 目标
<一句话说清要完成什么>

## 里程碑
- [ ] M1 调研与拆解：梳理依赖、列出风险
- [ ] M2 骨架落地：确定目录结构与函数签名
- [ ] M3 核心逻辑实现
- [ ] M4 测试与修复：补充单元测试并跑通
- [ ] M5 回归与文档：全量验证、更新 README

## 每个里程碑的验收标准
- M1：产出任务清单，标出依赖与风险点
- M2：目录结构与函数签名确定，可编译
- M3：核心功能可运行
- M4：所有测试通过
- M5：回归通过，文档更新完成
```

配套提示词写法：

```text
请先按上面的模板创建 PLANS.md，把本任务拆成多个里程碑。
规划得到我确认后，再逐步执行，每完成一个里程碑停下来汇报一次。
```

把大任务切成里程碑，既让 Codex 不至于做到一半跑偏，也让你能在关键节点及时纠偏。

### 3.3 迭代修复循环（iterative repair loops）

面对"测试挂掉、反复修反复错"的拉扯，官方推荐用**迭代修复循环**收敛：让 Codex 运行测试 → 收集失败原因 → 修复 → 再运行，循环直到全绿，而不是每次只让它"改一下再试试"。提示词写法：

```text
执行一次完整的修复循环：
1. 运行 pytest 收集所有失败用例；
2. 分析失败根因，按依赖顺序修复；
3. 修复后重新运行测试；
4. 若仍有失败，回到第 2 步，但每轮修复务必说明根因，禁止靠猜测反复试；
循环直到所有测试通过，最后输出根因清单和修复摘要。
```

关键在"每轮说明根因、禁止盲目试错"，否则循环会退化成碰运气。

## 四、提示词持久化：编码进 AGENTS.md

好提示词最大的敌人是"写一次、忘一次"。官方文档把这条模式列为关键：**prompt 一旦验证有效，就把它编码进 AGENTS.md，避免每次重复**。AGENTS.md 就是已验证提示词的持久层。

![已验证提示词沉淀进 AGENTS.md](/images/codex/prompts/02-prompt-to-agentsmd.png)

具体做法：

1. 在某个任务上试出有效 prompt（比如"测试用 pytest 跑、禁止动 src/config"）；
2. 提炼其中"可复用于本项目所有任务"的部分；
3. 写进项目根 `AGENTS.md` 或子目录级 `AGENTS.md`，按路径作用域生效；
4. 之后所有会话启动时自动加载，新任务无需再重复叮嘱。

值得区分的是它与记忆（Memory）的关系：AGENTS.md 管"怎么做"——结构、命令、约定、完成定义，塑造行为；记忆管"之前发生了什么"——先前工作中学到的有用上下文。两者的沉淀时机不同，但目标一致：把一次性的经验变成可复用的资产。

::: tip 建议
在 AGENTS.md 里维护一个"常用规则"区块，把项目约定、命令、完成定义集中存放。会话里发现某条 prompt 反复有效，就顺手把它沉淀进去——这正是官方推荐的关键模式。
:::

## 五、实战案例：完整重构提示词

把前面所有技巧合起来，看一个可复制的完整案例（任务：拆分一个耦合严重的支付函数）：

```text
背景：src/payments/process_order 耦合了支付、退款、对账逻辑，约 400 行，难以测试。
      技术栈：TypeScript + Express，测试框架为 Vitest，lint 使用 ESLint。

目标：把 process_order 拆分为 charge、refund、reconcile 三个函数，各自承担单一职责。

约束：
1. 不改变 process_order 的对外签名，入参、返回值保持完全兼容；
2. 保持现有错误码与日志格式不变；
3. 不引入新的第三方依赖。

验收标准：
1. 新增单元测试，覆盖拆分后的三个函数；
2. npm test 全部通过；
3. npx eslint . 无新增告警；
4. 现有测试全部回归通过。

完成后请：列出修改的文件清单，逐个说明每个文件改了什么、为什么这么拆。
```

对照三要素检查：目标明确（拆成三个函数）、约束清楚（兼容签名、错误码、无新依赖）、验收可执行（测试、lint、回归）。加上"输出文件清单"的要求，结果便于你审阅。

## 六、常见问题排查

| 问题 | 排查思路 | 解法 |
| --- | --- | --- |
| Codex 没按我的意思做 | 提示词缺约束或验收，模型只能靠猜 | 补全三要素，尤其是约束与验收标准 |
| 同样的任务每次结果不一致 | 规则只写在临时 prompt，没进 AGENTS.md | 把有效 prompt 编码进 AGENTS.md 持久化 |
| 任务太大，做到一半就停或跑偏 | 没有拆分里程碑 | 改用 PLANS.md 规划 + 分阶段执行 |
| 需求模糊，结果方向错误 | 没让 Codex 先澄清 | 使用 3.1 的反问澄清模式 |
| 修 bug 越修越乱 | 循环修复靠猜，没有根因分析 | 改用 3.3 的迭代修复循环 |
| 多轮后 Codex 忘了约定 | 长会话上下文被稀释 | 关键约定写入 AGENTS.md，或使用 `/memories` 查看记忆 |

## 七、总结

提示词是 Codex 最直接的交互界面，但它远不止"一句指令"：系统提示词、用户提示词、AGENTS.md 三层输入共同决定输出质量。写好提示词的核心是把握三要素——具体目标、约束条件、验收标准，再按官方 Prompting Guide 的要点补充位置、格式与背景。

遇到复杂场景，用三种进阶模式应对：模糊需求先反问澄清、长任务用 PLANS.md 规划、反复出错用迭代修复循环。最后别忘了最关键的一步：把验证有效的提示词编码进 AGENTS.md，让它沉淀为项目资产——一次写好，处处生效。这也是让提示词从"个人经验"升级为"团队规范"的分水岭。
