# 四、Cline 上下文管理

## 什么是上下文管理

上下文管理是 Cline 在整个对话过程中保持对项目理解的方式。可以将其理解为与 Cline 之间的共享工作空间——包含代码、决策、需求和进度。

## 上下文的三个层次

| 层次 | 内容 | 来源 |
|------|------|------|
| **即时上下文** | 当前对话和活动文件 | 当前会话 |
| **项目上下文** | 代码库结构、模式 | 自动发现 + @提及 |
| **持久上下文** | 记忆库、规则、文档 | 手动配置 |

## 上下文窗口

每个 AI 模型都有上下文窗口——单次对话中处理的最大信息量。用 Token 衡量。

| 模型 | 上下文窗口 | 有效限制 |
|------|-----------|----------|
| Claude 4 Sonnet | 200,000+ | ~150,000 |
| GPT-5 | 128,000+ | ~100,000 |
| Gemini 3.x | 1,000,000+ | ~400,000 |
| DeepSeek V3 | 64,000 | ~50,000 |

> Token 换算：1 Token ≈ 3/4 个英文单词；100 Token ≈ 3-5 行代码

## Cline 如何构建上下文

### 1. 自动上下文收集

启动任务时，Cline 主动发现：
- 项目结构和文件组织
- 导入关系和依赖项
- 代码模式和约定
- 配置文件和设置
- Git 历史（使用 @git 时）
- **VS Code 诊断信息**（TypeScript 错误、ESLint 警告、Problems 面板）——这是 Cline 的独特优势，无需手动运行 linter

### 2. 用户引导的上下文

- **@提及**：引用特定文件、文件夹或 URL
- **自然语言需求**：用描述性语言说明目标
- **分享截图**：提供 UI 上下文
- **规则和文档**：通过 `.clinerules` 或记忆库添加

### 3. 动态上下文适应

Cline 根据以下因素实时调整上下文重点：
- 任务复杂度
- 剩余上下文窗口空间
- 当前进度
- 错误消息和反馈
- 历史决策

## 自动上下文管理功能

### Focus Chain（焦点链，默认开启）

通过自动待办列表保持任务连续性。即使自动压缩运行后，关键上下文仍然可见。

### Auto Compact（自动压缩，始终开启）

上下文达到约 80% 时自动生成对话摘要，保留所有决策和代码变更，同时释放空间。

### 上下文截断

当对话接近窗口限制时，系统自动裁剪旧内容：
- **优先保留**：原始任务描述、最近的工具执行、当前代码状态
- **优先删除**：多余对话历史、已完成的工具输出、中间的调试步骤

### 子任务机制

当上下文使用量较高时，Cline 会自动发起新的子任务（new_task），把"对话摘要 + 必要文件"传递给子任务，清空旧上下文重新开始——这让它能够承接一小时以上的超长任务而不崩溃。

### 检查点（Checkpoint）

每一次 Agent 变更都会自动保存快照，可随时**一键撤销**回到任意之前的版本，相当于给 AI 编程上了保险。

## 最佳实践

### 基本原则（适用于所有 AI 编程工具）

| 建议 | 说明 |
|------|------|
| 保持常驻上下文精简 | `.clinerules` 塞太多会"优先级饱和"，反而降低效果 |
| 分散到条件注入 | 规则、技能、@提及按需加载，不要全部堆在常驻文件 |
| 保持会话简短 | 会话越长，"上下文腐化"和"指令衰减"越严重 |
| 验证放在上下文之外 | 测试、lint、CI/CD 不应依赖模型的上下文记忆 |
| 主动接近上限 | 用到 70-80% 时就开新任务，使用检查点兜底 |

### Cline 专属技巧

| 建议 | 说明 |
|------|------|
| 具体明确 | 清晰的目标帮助 Cline 理解需求 |
| 策略性 @提及 | 引用特定文件而非整个文件夹 |
| 监控进度条 | 黄色/红色时考虑使用 `/smol` 或 `/newtask` |
| 信任自动管理 | 焦点链和自动压缩自动处理复杂性 |
| 使用记忆库 | 记录持久的模式和约定 |
