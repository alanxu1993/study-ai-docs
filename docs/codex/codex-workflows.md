# Codex 官方工作流指南

很多开发者第一次用 Codex 时，都是"想到什么问什么"——顺手写个 prompt，看结果不对就再补一句。这种即兴式用法不是不行，但一旦任务变长、变复杂，很容易陷入"跑偏、返工、来回拉扯"的循环。OpenAI 官方在 Cookbook 里给出了一批**经过验证的工作流模式**，把"怎么用 Codex"从玄学变成了可复制的方法论。本章把这套官方工作流拆开讲透，让你无论处理单文件小改动，还是跨多模块的大重构，都能选对姿势、一次到位。

## 一、工作流核心概念：Skills 是官方推荐的可复用工作流机制

### 1.1 什么是"工作流"

工作流（Workflow）不是某个新功能，而是一套**固定的操作模式**：给定输入，按既定步骤，产出稳定结果。对应到 Codex，就是"什么样的任务用什么样的 prompt + 配套配置 + 执行节奏"。官方的态度很明确：与其每次临时发挥，不如把反复出现的流程沉淀下来，按流程走。

### 1.2 为什么 Skills 是官方推荐的载体

官方明确推荐用 **Skills** 作为可复用工作流机制。一个 Skill 就是一个文件夹，核心是 `SKILL.md`（用 YAML frontmatter 声明 `name` 和 `description`），还可以附带 `scripts/`、`references/`、`assets/`、`examples/` 等资源。相比一段 prompt：

| 对比维度 | 一段 prompt | 一个 Skill |
| --- | --- | --- |
| 承载内容 | 单条指令 | 指令 + 脚本 + 参考资料 + 示例 |
| 复用方式 | 复制粘贴，容易走样 | 一处定义，`/skills` 显式调用或按任务自动触发 |
| 团队共享 | 发到群里，版本混乱 | 放进 `.codex/skills/`，git 管理，全队一致 |
| 触发时机 | 手动粘贴 | 按 `description` 自动匹配任务 |

![Skills 承载可复用工作流](/images/codex/workflows/03-skill-workflow.png)

### 1.3 与普通脚本、MCP 的关系

三者是互补关系，别混用：**Skills 提供"怎么做"的指令**（含可执行脚本），**MCP 提供"能做什么"的外部工具**（数据库、浏览器、内部 API），**Hooks 在生命周期节点上自动触发**（比如改完代码自动格式化）。一个 Skill 内部可以调用脚本，也可以通过 `agents/openai.yaml` 的 dependencies 声明依赖 MCP 工具，组合使用才是完整形态。

## 二、规划-执行工作流：PLANS.md 模板

这是官方执行计划指南里的核心模式，专门针对**长任务、多步骤工作**。一句话：先规划，再执行，后检查。

![PLANS.md 规划-执行-检查](/images/codex/workflows/01-plan-execute.png)

### 2.1 适用场景

凡是"一步做完不现实"的任务都适用：跨多个模块的重构、新功能开发、技术债清理。特点是任务有明确目标但路径复杂，一步走错代价高。

### 2.2 三步走

1. **规划**：先用 PLANS.md 把任务拆成带检查点的步骤，写清每步目标、依赖、验收标准。**这段人工先写**，而不是直接让 Codex 开工——这是防止跑偏的第一道闸。
2. **执行**：把 PLANS.md 交给 Codex（可作为 prompt 附上，或让它在项目里读取），Codex 按计划逐步推进，**每完成一步停下来对照检查点**。
3. **检查**：在关键检查点人工 review，确认符合预期再放行下一步；发现问题就地修正计划。

### 2.3 PLANS.md 模板示例

```markdown
# 功能：订单模块迁移到新库存服务

## 目标
把订单模块从旧库存 API 迁移到新服务，不改业务行为。

## 计划
- [ ] Step 1：梳理旧调用点，列出全部受影响文件
      - 依赖：无
      - 验收：清单覆盖所有调用点
- [ ] Step 2：封装新客户端，保持接口签名兼容
      - 依赖：Step 1
      - 验收：编译通过，单测覆盖客户端
- [ ] Step 3：逐文件替换调用，跑通现有测试
      - 依赖：Step 2
      - 验收：全套测试通过
- [ ] Step 4：灰度验证 + 更新文档
      - 依赖：Step 3
      - 验收：线上观察无报错，文档同步

## 检查点
- Checkpoint A（Step 2 结束后）：人工 review 客户端接口
- Checkpoint B（Step 3 结束后）：跑全量测试并核对迁移前后行为
```

::: tip 提示
规划阶段让 Codex 辅助"脑暴拆分"没问题，但**最终计划要人工确认**。官方最佳实践是：prompt 里模糊的需求，先让 Codex 反问澄清，再落到 PLANS.md。
:::

### 2.4 检查的艺术

检查不是走马观花。至少要看三样：**是否偏离计划**（该做的做了没）、**是否引入新问题**（回归测试过没过）、**计划本身是否合理**（拆得太粗还是太细）。发现问题时，把修正直接写回 PLANS.md，Codex 后续步骤会沿着修正后的计划走，保持上下文连贯。

## 三、目标驱动工作流：Using Goals in Codex

规划-执行解决的是"一次长任务"，目标驱动解决的是"**持续多轮推进**"。官方 Cookbook 的 "Using Goals in Codex" 给出了这一模式：在 ChatGPT / Codex 中设置**长期目标**，Agent 自动朝目标推进，而不是每次重新开话题。

### 3.1 什么是 Goals

Goals 是把"想达成什么"从单次会话里抽出来，变成一个跨会话持续生效的锚点。对比任务驱动：

| 维度 | 任务驱动（Task-driven） | 目标驱动（Goal-driven） |
| --- | --- | --- |
| 驱动单元 | 单条 prompt | 长期目标 |
| 会话关系 | 每次独立 | 跨会话延续 |
| 谁来推进 | 用户不断下指令 | Agent 在目标框架内自动推进 |
| 适用场景 | 明确的小任务 | 多轮迭代、长期维护、渐进改进 |

![Goals 长期目标推进](/images/codex/workflows/02-goals.png)

### 3.2 目标怎么设才有效

一个坏目标："让项目更好"。一个好目标："把测试覆盖率从 60% 提升到 80%，并让 CI 在合并前强制跑测试"。好目标具备三要素：**可衡量**（有数字）、**有边界**（不越界改无关代码）、**可分步**（Agent 知道自己该先做什么）。设置后，后续会话里 Agent 会自动检查当前进展、主动规划下一步，而不是等用户逐条指示。

::: warning 注意
目标驱动不等于"放了目标就撒手不管"。Agent 自动推进是**在既定边界内**，关键节点仍需人工把关。尤其涉及对外发布、数据迁移等高风险动作，始终保留最终审批权。
:::

### 3.3 与 AGENTS.md 的配合

Goals 是"要达成什么"，AGENTS.md 是"按什么规矩做"。两者配合最佳：AGENTS.md 固定工程约定（构建命令、编码风格、完成定义），Goals 设定长期方向。这样 Agent 既知道方向，也知道底线，不会为了冲目标而破坏项目约定。

## 四、迭代修复工作流：Build iterative repair loops

官方 Cookbook 的 "Build iterative repair loops with Codex" 给出了开发中最常见、也最该自动化的一环：**构建-测试-修复循环**。

### 4.1 循环模型

核心是一个闭环：`构建 → 测试 → 拿到失败信息 → 修复 → 再构建`。人工守着这个循环最耗耐心（跑一次测试、看一眼日志、改一行、再跑），而 Codex 恰恰擅长这个单调环节——给它失败信息，它定位修复，再验证。

```
┌──────────────────────────────────────────┐
│  构建/测试失败 → Codex 读失败日志         │
│     ↓                                    │
│  定位根因 → 修改代码 → 重新构建测试       │
│     ↓                                    │
│  仍失败？→ 继续迭代       通过？→ 收尾   │
└──────────────────────────────────────────┘
```

### 4.2 四个步骤

1. **建立可复现的失败基线**：先跑一次，确认当前失败点可稳定复现。基线都跑不稳，修复无从谈起。
2. **让 Codex 单点修复**：把失败日志喂给 Codex，明确要求"只修这一个问题，先解释根因再动手"。
3. **自动回归验证**：修完立刻重跑，验证是否引入回归。
4. **限定迭代轮次**：给循环设上限（比如最多 5 轮），防止 Codex 陷入盲目打补丁。

### 4.3 用 Hooks 加固修复结果

修复循环的终点是"代码能跑"，但"能跑"不等于"符合规范"。可以配合 Hooks 在 `PostToolUse` 或 `Stop` 事件自动跑格式化、lint 或安全扫描，把规范检查也并入循环：

```json
// .codex/hooks.json（示意，以官方文档为准）
{
  "PostToolUse": [
    {
      "matcher": "Write|apply_patch",
      "command": "npx prettier --write \"$(git diff --name-only)\""
    }
  ]
}
```

::: tip 提示
官方反复强调 CI 失败的最后 10% 问题（缩进、换行、格式）不值得占用主代理的注意力。把格式化这类确定性检查交给 Hooks，主代理专注逻辑修复。
:::

## 五、一致工作流：Codex CLI & Agents SDK 组合、workspace agents

前几节解决"单个 Codex 会话"的工作流，这一节解决**规模化、团队化的一致性问题**。

### 5.1 Codex CLI + Agents SDK：规划与执行分离

官方 Cookbook "Building Consistent Workflows with Codex CLI & Agents SDK"（2025-10）提出一个组合：**Codex CLI 负责生成高质量规划，OpenAI Agents SDK 负责执行**。

工作流是：先用 Codex CLI 分析任务、产出实现计划（利用它对代码库的深度理解），再把这个计划交给 Agents SDK 编排的多个 Agent 分步执行。每个执行 Agent 挂上统一 guardrails（比如强制读 AGENTS.md、禁止改测试文件、限制工具权限），**所有人产出的代码风格和约束一致**。这样既拿到 Codex 的规划质量，又获得 Agent 管线的规模化和可控性。

### 5.2 ChatGPT 里的 workspace agents

官方 Cookbook "Building workspace agents in ChatGPT"（2026-05）把同一理念搬进 ChatGPT：在云端沙箱中创建 workspace agents，它们能访问 GitHub 仓库、在隔离环境里改代码、提交 PR。适合的场景是**团队共享的例行任务**——比如"每周清理过期依赖"、"修所有 lint 告警"，定义一个 agent 反复跑，而不是每次都重新解释需求。

### 5.3 一致性从哪来

不管哪种组合，一致性的根基是**统一的约束层**：AGENTS.md（工程约定）+ 统一的 hooks（自动化检查）+ 统一的 skills（标准工作流）。谁执行、在哪执行可以变，约束层不变，产出就一致。把这三样放 git 仓库里随项目分发，是保证团队一致性的最低成本做法。

## 六、工作流实践对比表

| 工作流 | 核心机制 | 解决什么问题 | 何时选用 |
| --- | --- | --- | --- |
| 规划-执行 | PLANS.md 模板 | 长任务跑偏 | 多步骤重构/功能开发，任务大而路径复杂 |
| 目标驱动 | Goals | 跨会话持续推进 | 长期维护、渐进改进、多轮迭代 |
| 迭代修复 | 构建-测试-修复循环 | 修 bug 耗耐心 | 反复失败/回归，需要自动化回归验证 |
| 一致工作流 | CLI + Agents SDK / workspace agents | 团队规模产出不一致 | 多人协作、例行任务标准化、CI 管线集成 |
| Skills 复用 | SKILL.md 打包 | 流程无法沉淀 | 任意流程一旦验证有效，立刻技能化 |

::: warning 避坑
这几种工作流不是互斥的，真实项目常叠加使用：用 PLANS.md 规划一个大版本 → 用迭代修复循环消化回归 → 把验证有效的步骤沉淀成 Skill → 长线目标用 Goals 持续跟踪。
:::

## 七、最佳实践

1. **先沉淀，再放大**：任何 prompt 一旦验证有效，立即编码进 AGENTS.md 或 Skill，别靠记忆和复制粘贴。
2. **规划是人机协作**：机器擅长老实执行，人类擅长判断方向。规划的最终确认权始终在人。
3. **给循环设边界**：迭代修复、目标推进都设上限和检查点，防止无限循环烧时间烧 token。
4. **统一约束层**：AGENTS.md + hooks + skills 放仓库版本管理，是规模化一致性的基础设施。
5. **高风险动作人工审批**：涉及发布、数据、权限的步骤，保持人工兜底。

## 总结

官方工作流的精髓可以浓缩成三句话：**短流程靠 Skills 沉淀，长任务靠 PLANS.md 规划，持续改进靠 Goals 和 repair loop 驱动**。这四种模式外加"规划与执行分离"的一致工作流，覆盖了从个人单次改动到团队规模交付的全部典型场景。下一章我们将把这些工作流真正落地——按项目、团队、个人三个维度定制 Codex，让工作流和你的项目血肉相连。
