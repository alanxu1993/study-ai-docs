# Codex Plugins 使用教程

现实中，把 Skills、MCP 服务器、Hooks 和团队资源一个个手工配置到每台开发机，费时又容易漏配；换台机器、新同事入职，环境就"飘"了，规则也因人而异。Plugins 正是为解决"能力打包与分发"而生的机制——把一组相关的 Skills、MCP 配置、Hooks 与应用集成打包成一个**可安装的分发单元**，一次安装、团队统一生效，优秀实践真正做到"一处沉淀、处处复用"。

本教程从插件核心概念讲起，逐层拆解插件的内部结构、安装与使用、如何构建自己的插件，并用团队分发与 GitHub 集成的实战案例演示完整链路。所有目录结构与配置均给出可直接套用的模板。

## 一、插件核心概念

![插件打包多种能力](/images/codex/plugins/01-plugin-package.png)

### 1.1 什么是插件（一句话懂）

插件是 Codex 的**可安装分发单元**：把若干相关的能力——Skills、MCP 服务器、Hooks、应用集成与资源——统一打包，通过一条安装流程部署进环境，供个人或团队共享使用。

类比理解：Skill 是"一份菜谱"（创作格式），插件则是"一盒成品调料包"（安装单元）。菜谱还是那份菜谱，但插件把配方、配料、加热说明都装进一个盒子，开箱即用，不用每次自己按原料拼装。

### 1.2 插件与 Skill、MCP 的关系

三者经常被混淆，但定位完全不同。用一句话区分：**Skill 是创作格式，插件是可安装分发单元，MCP 是工具协议**。

| 概念 | 本质 | 解决什么问题 | 粒度 |
| --- | --- | --- | --- |
| Skill（技能） | 创作格式，一份工作流指令 | "教 Agent 怎么做一件事" | 单个工作流 |
| MCP 服务器 | 工具协议，外部能力接入 | "给 Agent 提供能用的工具" | 单个/多个工具 |
| Plugin（插件） | 分发单元，打包与安装 | "把一堆能力装到环境里" | 一组能力 |

三者的协作关系：

- **Skill 是创作格式**：用 `SKILL.md`（YAML frontmatter 声明 name、description）写好工作流，放进 skills 目录即可被调用，是最轻量的能力单元；
- **MCP 是工具协议**：注册一个 MCP 服务器，Codex 就多了一批以 `mcp__<server>__<tool>` 形式暴露的工具；
- **插件是分发单元**：把 Skills、MCP 配置、Hooks、脚本与资源一起装进一个单元，借助安装机制统一部署、统一版本。

一句话总结：Skill 和 MCP 是"造东西"，插件是"打包发货"。

### 1.3 为什么要用插件（核心价值）

1. **消除重复配置**：团队 10 台机器手工配 5 样东西就是 50 次操作，插件一次安装全部搞定，新人入职从"折腾半天"变成"一条命令"；
2. **版本统一**：插件带版本，升级只需更新插件版本，避免各人环境漂移、行为不一致；
3. **能力复用**：把沉淀好的技能、工具、钩子固化成一个"能力包"，新项目、新成员开箱即得；
4. **生态分发**：官方与社区发布的插件可直接安装，不用自己从零造轮子。

## 二、插件包含什么

### 2.1 插件的组成部分

一个插件内部通常由五类内容组成：

| 组成 | 说明 | 示例 |
| --- | --- | --- |
| SKILL.md | 核心技能文件，定义工作流指令（必需） | `SKILL.md` |
| scripts | 插件命令与辅助脚本，运行时接收环境变量 | `scripts/xxx.sh` |
| MCP 配置 | 随插件注册的 MCP 服务器 | `mcp_config.json` |
| hooks 配置 | 随插件部署的生命周期钩子 | `hooks.json` |
| resources | 引用/示例/资产等辅助资料 | `references/`、`examples/`、`assets/` |

### 2.2 SKILL.md 与 scripts

SKILL.md 是插件的"说明书 + 工作流"，必须包含 YAML frontmatter，其中 `name` 和 `description` 为必填项：

```
---
name: my-plugin-workflow      # 必填，小写连字符，须与目录名一致
description: 用于……的代码审查工作流  # 必填，作为模型触发条件，不是摘要
---
（工作流正文……）
```

scripts 是插件内的可执行脚本，其中一部分是"插件命令"——插件安装后，Codex 可按需调用这些命令。它们运行时会收到 `PLUGIN_ROOT` 与 `PLUGIN_DATA` 两个环境变量（见 3.3 节），据此定位插件资源或读写运行状态。

### 2.3 MCP 与 hooks 配置

- **MCP**：插件随带 MCP 服务器配置，安装后注册为 `[mcp_servers.<id>]`（注意是 snake_case，不是 mcpServers），工具以 `mcp__<server>__<tool>` 暴露给 Codex；
- **Hooks**：插件可带 hooks 配置，安装后对应 `.codex/hooks.json` 或 config.toml 内联 `[[hooks.<EventName>]]` 块，可覆盖 `SessionStart`、`PreToolUse`、`PostToolUse`、`SubagentStop`、`Stop` 等事件。注意：hooks 需要开启 `codex_hooks` 特性开关（v0.124 起稳定），否则不会执行。

::: warning hooks 需要特性开关
插件自带的 hooks 默认不会自动生效，先确认环境已启用 `codex_hooks` 特性，否则插件里的钩子形同虚设。
:::

### 2.4 资源文件

`references/`、`examples/`、`assets/` 存放供技能与脚本引用的辅助资料，安装后随插件一起落地。脚本在运行时通过 `PLUGIN_ROOT` 环境变量定位这些资源，做到"插件搬到哪都能找到自己的东西"。

## 三、插件的安装与使用

![插件安装分发流程](/images/codex/plugins/02-plugin-distribution.png)

### 3.1 从仓库安装

插件的安装入口与说明维护在 `/codex/plugins` 文档页。一般流程如下：

1. **获取插件**：从插件仓库、分享源拿到插件（源码仓库或已打包形式）；
2. **执行安装**：安装到环境，使其被 Codex 识别；
3. **查看与启用**：列出已安装插件，确认目标插件就位。

```bash
# 安装插件（命令以官方文档为准，不同版本可能不同）
codex plugins install <插件名或仓库地址>

# 查看已安装插件
codex plugins list
```

::: tip 以官方文档为准
插件 CLI 命令随版本演进，本教程只保证概念流程正确；执行前请以 `/codex/plugins` 官方文档页为准，确认你当前版本的确切命令。
:::

### 3.2 启用与配置

插件安装后，通常还需在配置中启用并按需调整，例如：指定要注册的 MCP 服务器、决定是否加载插件携带的某个 Skill、调整 hooks 触发的具体事件。配置完成后**重启会话**使其生效——大多数"装了没反应"都源于会话未刷新。

### 3.3 PLUGIN_ROOT 与 PLUGIN_DATA 环境变量

插件命令（scripts）运行时，Codex 会注入两个环境变量：

| 变量 | 含义 | 典型用途 |
| --- | --- | --- |
| `PLUGIN_ROOT` | 插件安装根目录 | 定位插件自带的 SKILL.md、references、模板等只读资源 |
| `PLUGIN_DATA` | 插件数据目录 | 持久化插件状态、缓存、生成的配置 |

在脚本中通过这两个变量引用路径，插件就具备了可移植性：

```bash
#!/usr/bin/env bash
# 读取插件自带资源
SKILL_PATH="$PLUGIN_ROOT/SKILL.md"
TEMPLATE_DIR="$PLUGIN_ROOT/references/templates"

# 在数据目录写入运行时状态（跨调用保留）
echo "$(date)" >> "$PLUGIN_DATA/run.log"
```

### 3.4 验证插件是否生效

- 用 `/skills` 查看插件携带的技能是否出现在列表；
- 触发插件配置的 hook 事件，确认日志或副作用出现；
- 若插件注册了 MCP 服务器，检查 `mcp__<server>__*` 工具是否可用。

## 四、构建自己的插件

### 4.1 构建流程要点

官方文档 `/codex/plugins/build` 提供插件构建指南，核心思路一句话：**把一组相关能力规整成一个标准目录，声明好元信息，让安装机制能识别、装载并配置它**。要点如下（细节以官方文档为准）：

- **定边界**：先明确插件要打包什么——纯 Skill？Skill + MCP？还要不要 hooks？
- **守结构**：遵守目录结构约定，让安装器能识别各组件；
- **写脚本**：插件命令正确消费 `PLUGIN_ROOT` / `PLUGIN_DATA`，别写死路径；
- **写好 SKILL.md**：name 与目录一致、description 足够具体，模型才能准确触发。

### 4.2 打包目录结构

一个典型插件的目录结构：

```
my-plugin/
├── SKILL.md              # 核心技能文件（必需）
├── scripts/
│   ├── build.sh          # 插件命令：一键构建
│   └── scan.sh           # 插件命令：安全检查
├── mcp_config.json       # MCP 服务器配置（可选）
├── hooks.json            # hooks 配置（可选）
├── references/           # 引用资料（可选）
├── examples/             # 示例（可选）
└── assets/               # 静态资产（可选）
```

::: tip 从 Skill 起步
如果不确定要不要做插件，先把工作流写成一个 Skill（放在 `~/.codex/skills/` 或项目 `.codex/skills/`），验证有效后，再把它连同 MCP、hooks 一起打包成插件分发。Skill 是插件的"内核"，插件是 Skill 的"外壳"。
:::

### 4.3 分发你的插件

构建完成后即可对外分发：推送到 Git 仓库、内部私有源，或分享给团队统一安装。分发时务必附上 README，说清三件事——插件包含哪些能力、需要什么环境（如 hooks 需开启 `codex_hooks`）、有什么注意事项（如需要哪些权限）。

## 五、实战案例

### 5.1 案例一：团队统一开发规范插件

场景：团队要求所有项目遵循同一套规范——代码审查流程、构建脚本、提交前 lint 校验。

- **SKILL.md**：定义"代码审查工作流"，约定审查清单与通过标准；
- **scripts/lint.sh**：一键执行 lint + 单元测试；
- **hooks.json**：`PreToolUse` 对危险命令（如 `rm -rf`、`git push --force`）做拦截；
- **MCP 配置**：接入团队内部 API（如缺陷追踪系统），让审查时可查询工单。

团队把该插件纳入统一基线，新人入职一条命令完成环境配置，规范不再靠口头传达、靠文档翻找。

### 5.2 案例二：集成 GitHub 工作流的插件

场景：把 GitHub 相关操作整合成一个插件，让开发者在任意项目复用同一套流程。

- **SKILL.md**：定义"创建 PR 工作流"，从分支命名、提交信息到 PR 描述都有模板；
- **scripts/gh-pr.sh**：调用 GitHub CLI 自动创建 PR；
- **hooks.json**：`PostToolUse` 在代码编辑后自动格式化并跑 lint，避免 CI 失败的"最后 10%"问题。

安装该插件后，无论新老项目，GitHub 工作流体验完全一致，团队的 PR 质量基线也随之抬高。

## 六、最佳实践与常见问题

### 6.1 最佳实践

- **单一职责**：一个插件聚焦一类能力，便于维护、组合与故障定位；
- **脚本用相对路径**：所有资源一律通过 `$PLUGIN_ROOT` 定位，别写死绝对路径；
- **随带说明**：注明依赖的特性（如 `codex_hooks`）、需要的权限、支持的 Codex 版本；
- **统一入口**：团队用内部插件仓库统一管理版本，避免各自维护、版本分叉。

### 6.2 常见问题排查

| 问题 | 排查步骤 |
| --- | --- |
| 插件安装后技能看不到 | 重启会话；检查 SKILL.md frontmatter 的 `name` 是否与目录一致、`description` 是否清晰 |
| hooks 不生效 | 确认已开启 `codex_hooks` 特性；确认 hooks 配置落在安装后的 `.codex/hooks.json` |
| MCP 工具不可用 | 检查 `mcp_servers` 是否 snake_case 命名；确认服务器能正常启动 |
| 脚本找不到资源 | 检查是否用 `$PLUGIN_ROOT` 定位资源，而不是硬编码本地路径 |
| 插件命令报权限错 | 检查审批模式与 `default_tools_approval_mode` 是否覆盖插件命令所需工具 |

::: warning 不要混淆安装与创作
Skill 是创作格式，放进 skills 目录即生效；插件是需要安装的分发单元。直接把插件目录当 skill 目录拷贝，可能因缺少安装与注册步骤而不生效。
:::

## 七、总结

插件把 Skills、MCP、Hooks 与资源统一包装成可安装的分发单元，让"能力沉淀 → 打包 → 团队分发"成为一条完整链路。用好插件，团队能显著减少重复配置、统一工具版本、让优秀实践一次落地、处处生效。理解了"Skill 是创作格式、插件是分发单元、MCP 是工具协议"三者的分工，你就掌握了 Codex 能力体系的装配思路。下一章我们将探讨 Rules——用 AGENTS.md 承载持久指令，从行为层面进一步规范 Agent。
