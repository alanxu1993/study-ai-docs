# Codex 最佳实践

前几章给了你概念、定制方法和可复制示例——现在缺的是一根把这一切串起来的准绳。很多配置单独看都对，组合起来却事倍功半：AGENTS.md 写得像本小说、prompt 每次临时发挥、特性一锅全开、审批要么过松要么卡死。本章把官方 Best Practices 指南与社区真实经验浓缩成**一套可执行的方法论**，回答同一个问题：怎么让 Codex 在长期使用中既高效又不失控。

## 一、AGENTS.md 最佳实践：简短、进化、闭环

AGENTS.md 是 Codex 的"灵魂"，但也恰恰是最容易被写废的文件。

### 1.1 保持简短：写必要的规矩，别写小说

AGENTS.md 不是设计文档，是**给 Agent 的约束清单**。一段话能说清的事别写三页——规则太多会被稀释，Agent 反而抓不住重点。一个实用的判断标准：**这条规则如果删掉，Agent 是否可能犯错？** 不会，就删。保留的每条都得是"不遵守就会出问题"的硬约束。

```markdown
<!-- 反例：写成了散文 -->
本项目的代码应当具有良好的可读性和可维护性，
请确保代码质量……（五百字赞美）

<!-- 正例：可执行的硬约束 -->
- 命令：`npm test` 必须通过
- 禁止：修改 `dist/`、`node_modules/`
```

### 1.2 规则来自反复犯错

官方明确建议：**AGENTS.md 的规则应该来自你反复踩过的坑，而不是开工前空想**。让 Agent 跑一段时间，观察它在哪里犯错，把每个真实错误补成一条规则。这样沉淀出的 AGENTS.md 天然贴合你的项目，而不是一堆放之四海而皆准的废话。

### 1.3 反馈闭环：AGENTS.md 是已验证 prompt 的持久层

官方提示词最佳实践有一条关键原则：**prompt 一旦验证有效，就编码进 AGENTS.md**，避免每次重复。这构成一个闭环：`实践 → 验证 → 沉淀 → 复用`。你花半小时打磨出的有效 prompt，是项目资产，不是一次性消耗品。

## 二、提示词最佳实践：先澄清，再沉淀

### 2.1 模糊需求，让 Codex 反问

官方 Prompting Guide（2026-02）的核心里有一句：需求模糊时，**先让 Codex 反问问题**澄清，而不是硬猜。直接丢一句"帮我优化一下性能"然后期待它一次到位，是把模糊的锅甩给 Agent。

```text
用户（模糊）：帮我优化一下这个模块的性能。

更优写法：先让它澄清——
"这是一个加载慢的问题吗？还是内存问题？
请先反问我：目标函数、当前瓶颈、性能指标、可接受的改动范围，
然后给出方案再动手。"
```

澄清后再让 Codex 制定方案（长任务用 PLANS.md 模板），你确认后它再执行。这比"猜错 → 返工"省的时间多得多。

### 2.2 验证后沉淀，拒绝重复劳动

每次发现"这个 prompt 效果很好"，问自己一句：**它值得被复用吗？** 值得，就沉淀。验证有效的指令进 AGENTS.md，验证有效的流程进 Skill，验证有效的工具配置进 `.codex/`。沉淀是防止个人经验流失的唯一手段。

## 三、配置最佳实践：分层、克制、平衡

### 3.1 配置分层：行为规则 vs 持久规则

官方规则体系建议明确分工：

| 规则类型 | 特征 | 放哪里 |
| --- | --- | --- |
| 行为规则 | 有确定性设置的（审批策略、模型参数、沙箱模式） | config.toml（含 profiles） |
| 持久规则 | 结构、命令、约定、完成定义 | AGENTS.md |

行为规则靠配置强制执行，持久规则靠指令约束。混放的结果是：改配置时找不到，改指令时又怕影响别的项目。

### 3.2 特性按需开启，不要一锅全开

Codex 有很多特性开关（`codex features list` 查看）。默认全关是合理的保守起点，按需开启：需要 Plan 模式再开 `collaboration_modes`，需要钩子再开 `codex_hooks`，需要智能审批再开 `request_rule`。**每开一个特性都要回答"它解决了我的哪个问题"**，开而不用的特性只会增加不可预测性。

```bash
codex features list          # 查看全部特性及状态
codex features enable codex_hooks    # 按需开启
codex --disable image_generation     # 或会话内临时关闭
```

### 3.3 审批模式：安全与效率的平衡

审批模式是安全和效率的拉锯。过度保守（每个操作都问）会打断流、消磨耐心；过度放开（全自动）在复杂项目里有破坏风险。建议按风险分级：

| 操作类型 | 建议策略 |
| --- | --- |
| 读操作、测试、格式化 | 放行（`default_tools_approval_mode = "approve"`） |
| 编辑非关键文件 | 直接放行或快速审批 |
| 删文件、改配置、高权限 shell | 审批 |
| 生产数据、发布、密钥相关 | 强制人工 + 用 hooks `PreToolUse` 双保险拦截 |

::: tip 提示
`request_rule`（智能审批）值得一试：它会根据操作风险自动决定该放行还是该问，能省掉大量低风险操作的确认步骤，又不牺牲高风险操作的安全。
:::

## 四、Hooks/Skills/MCP 组合最佳实践

三类机制各管一段，组合的正确姿势是**把确定性的交给机器，把经验性的沉淀成技能，把外部的接进来**：

1. **Hooks 管"必然要做的确定性动作"**：格式化、lint、安全扫描、日志。它们不依赖模型判断，交给 hooks 永远稳定执行，顺带根治 CI 最后 10% 的失败。
2. **Skills 管"重复出现的经验性流程"**：代码审查、发版检查、加字段流程。把验证有效的工作流技能化，团队复用。
3. **MCP 管"Codex 自己够不到的外部能力"**：数据库、浏览器、内部 API。只接项目真正需要的，别为了"能力多"堆一堆用不上的服务器。

一个常见误区是**把三者混用**：拿 prompt 反复描述格式化规则（应该用 hooks）、拿 MCP 挂一堆无关服务（应该克制）、拿 Skill 当脚本仓库（应该只装流程）。各司其职，组合才有性价比。

## 五、团队与个人工作流最佳实践

### 5.1 团队：一致优先

- **共享约束层进仓库**：AGENTS.md、`.codex/`、hooks、plugins 全部 git 管理，随仓库分发，杜绝口口相传。
- **统一插件分发**：把团队标准工具箱打包成 Plugin，成员装一次即可获得一致环境。
- **PR 评论委派**：团队协作时，可在 GitHub PR 评论 `@codex` 委派任务，把 Codex 纳入现有协作流而不是另起炉灶。
- **Codex 与 Agents SDK 组合**：规划用 Codex CLI、执行交给 Agents SDK 编排，靠统一 guardrails 保证多人产出一致。

### 5.2 个人：效率优先

- **个人偏好只放全局**：`~/.codex/AGENTS.md`（每次会话都读）+ `~/.codex/skills/`（跨项目技能）+ profiles 快速切换场景。
- **记忆要主动沉淀**：用 `/memories` 查看记忆，把值得记住的上下文显式保存，别指望 Codex 全自动记住所有事。
- **日常用对工具**：交互式开发用 `codex`，CI 管线/批处理用 `codex exec "<prompt>"`，批量管理用斜杠命令（`/fork`、`/resume`、`/init`、`/skills`）。

### 5.3 持续审视：怎么知道自己在进步

最佳实践不是一次性做完，而是长期演进。给自己设三个可观测的信号，每月复盘一次：

| 信号 | 怎么看 | 理想趋势 |
| --- | --- | --- |
| 重复劳动在减少 | 同一类任务，是否还要每次重新描述需求 | 越来越少，因为沉淀进了 AGENTS.md / Skills |
| 返工在减少 | 长任务跑偏、改错的次数 | 越来越少，因为 PLANS.md 规划 + 检查点 |
| 事故在减少 | 破坏性操作、CI 挂掉、格式问题 | 越来越少，因为 hooks + 审批分级兜底 |

三个信号都持续向好，说明你踩的坑真正转化成了项目的规则和工具；信号停滞，就回头审视是哪一层没做透——通常卡在"验证有效却忘了沉淀"。

## 六、避坑清单：常见误区

![常见坑避让](/images/codex/best-practices/02-avoid-pits.png)

| 误区 | 真实后果 | 正确做法 |
| --- | --- | --- |
| AGENTS.md 写成长篇小说 | 规则被稀释，Agent 抓不住重点 | 只留硬约束，一条一屏内可读完 |
| prompt 重复发明轮子 | 每次质量参差，经验流失 | 验证有效即沉淀进 AGENTS.md / Skill |
| 特性一锅全开 | 行为不可预期，排查困难 | `features list` 查看，按需逐个开 |
| 审批要么全放行要么全卡死 | 安全失控或效率归零 | 按风险分级，`request_rule` 智能审批 |
| 用 prompt 描述格式化规则 | 浪费 token，还不稳定 | 交给 Hooks 确定性执行 |
| MCP 挂一堆用不上的服务 | 启动慢、噪音多、安全隐患 | 只接项目真正需要的 |
| 团队配置靠聊天群同步 | 版本漂移、成员环境不一致 | 全部进仓库 git 分发 |
| 让 Codex 在关键动作上全自主 | 不可逆操作（删除/发布）出事 | 高风险保留人工审批 + hooks 兜底 |
| 忽略记忆沉淀 | 跨会话上下文断裂，重复解释 | `/memories` 查看，主动保存关键上下文 |
| 长任务不规划直接开工 | 中途跑偏，返工成本高 | PLANS.md 先规划，分步检查点 |

::: warning 最贵的教训
这些坑里，**"规则不沉淀"和"长任务不规划"是最贵的两个**——它们不是单次事故，而是持续性的效率漏损。前者让你的经验永远无法积累，后者让每个长任务都在赌运气。
:::

### 6.1 上手自查清单

如果你刚开始使用，用这份清单做一次"健康检查"，逐项打勾：

- [ ] AGENTS.md 已存在，一屏内能读完，只含硬约束
- [ ] 每个验证有效的 prompt 都已沉淀（AGENTS.md / Skill）
- [ ] 长任务走 PLANS.md：先规划、分步执行、有检查点
- [ ] 格式化/lint 已交给 Hooks，不占主代理注意力
- [ ] 审批按风险分级，高风险操作保留人工审批
- [ ] MCP 只接了项目真正需要的服务器
- [ ] 团队配置全部进仓库 git 分发，非口口相传
- [ ] 每季度按"重复劳动/返工/事故"三信号复盘一次

超过 5 项没勾，说明还有明显的效率漏损可以补；全勾了，你的 Codex 基本处于健康运行状态。

## 七、总结

Codex 的最佳实践，本质上是一组"**把不确定性转变成确定性**"的动作：用 AGENTS.md 把规矩固化，用沉淀把经验复用，用 hooks 把重复自动化，用分级审批把风险收口，用仓库分发把团队拉齐。工具本身的门槛不高，拉开差距的从来不是"会不会配"，而是**有没有把这些动作变成习惯**。把这六条原则贯穿到日常，Codex 就从一个偶尔惊艳的助手，变成一个稳定可预期的生产力工具。至此，从安装到工作流、从定制到示例、从方法论到避坑，Codex 的完整使用链路就通了——剩下的，交给你的项目去验证。
