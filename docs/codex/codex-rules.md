# Codex Rules 使用教程

每次会话都靠 prompt 反复叮嘱"记住构建命令""别忘了跑测试"，Agent 还是会忘——因为指令没有持久化。Rules（规则）正是解决这一问题的机制：用 AGENTS.md 承载一份**持久指令体系**，会话开始时自动加载，让 Agent 从第一步就"懂规矩"，不用每次重新交代。

本教程从规则体系的核心概念讲起，理清 Rules 与 AGENTS.md、config.toml 的分工，再讲到规则层级、编写技巧、加载时机与作用域，末尾给出团队、个人、子目录三个实战案例和可直接复制的 AGENTS.md 模板。

## 一、规则体系核心概念

### 1.1 什么是 Rules（一句话懂）

Rules 是 Codex 的**持久指令体系**，载体是 AGENTS.md——一份"给 Agent 看的 README"。它随会话自动加载，持续塑造 Agent 的做事方式，而不是每次靠 prompt 临时口头交代。

类比理解：prompt 是"口头吩咐"，Rules 是"写在墙上的规矩"。口头吩咐说完就忘，墙上的规矩每次开工都看得见、照着做。

一个典型场景最能说明问题：没有规则时，你每开一个会话都要把"构建命令是什么、测试怎么跑、哪些文件不能动"重新交代一遍，漏一句 Agent 就可能跑偏；有了 AGENTS.md 之后，这些约定一次性写定、随会话自动加载，Agent 的行为从"碰运气"变成"有规矩可依"。

### 1.2 Rules 与 AGENTS.md、config.toml 的关系

三者是"统称、载体、配置"的关系：

| 概念 | 本质 | 存放位置 | 例子 |
| --- | --- | --- | --- |
| Rules | 规则体系的统称 | 贯穿 AGENTS.md 与 config.toml | "先写测试再实现" |
| AGENTS.md | 持久规则的载体文件 | 仓库根、子目录、`~/.codex/` | 构建命令、PR 期望、完成定义 |
| config.toml | 确定性行为配置 | `~/.codex/config.toml`、`.codex/config.toml` | 模型、审批模式、沙箱 |

AGENTS.md 是规则的载体，同时支持 **persona（角色）作用域与路径作用域**两类规则（细节以官方文档为准）；而 config.toml 承载的是带确定性开关的行为配置。两者共同构成完整的规则体系。

### 1.3 规则放哪：AGENTS.md 还是 config.toml？

![规则 vs 行为配置](/images/codex/rules/03-rules-vs-config.png)

核心原则一句话：**持久规则放 AGENTS.md，确定性行为规则放 config.toml**。

- **持久规则 → AGENTS.md**：仓库结构、构建/测试/lint 命令、工程约定、PR 期望、完成定义（definition of done）、do-not 规则——这些是"项目知识"，需要随项目版本管理、跟随仓库分发；
- **确定性行为规则 → config.toml**：模型名与 `temperature`、审批模式 `approval_policy`、默认工具审批 `default_tools_approval_mode`、沙箱 `sandbox_mode`——这些是有明确开关的机器行为，写进配置文件即可，不必占用 AGENTS.md 篇幅。

| 判断维度 | 放 AGENTS.md | 放 config.toml |
| --- | --- | --- |
| 内容性质 | 项目知识 / 约定 | 机器行为开关 |
| 谁读 | Agent 每次会话读 | 运行时按配置执行 |
| 典型例子 | 构建命令、完成定义、do-not | 模型名、审批策略、沙箱模式 |
| 管理方式 | 随仓库版本控制 | 配置文件统一管理 |

## 二、规则层级

### 2.1 三层规则体系

![多层规则体系](/images/codex/rules/01-rules-layers.png)

| 层级 | 位置 | 生效范围 | 典型用途 |
| --- | --- | --- | --- |
| 全局规则 | `~/.codex/AGENTS.md` | 每次会话都读 | 个人通用约定、全局 do-not |
| 项目规则 | 仓库根 `AGENTS.md` | 该项目内生效 | 团队规范、构建命令、PR 期望 |
| 子目录规则 | 子目录 `AGENTS.md` | 该目录及其子目录 | 局部模块的专属约定 |

此外，Codex 支持项目内使用 `.codex/AGENTS.md` 放置 Codex 特定的补充规则，与仓库根 AGENTS.md 配合使用。

### 2.2 嵌套级联：越近优先级越高

![嵌套 AGENTS.md 级联生效](/images/codex/rules/02-nested-cascade.png)

AGENTS.md 支持**嵌套级联**：子目录中的 AGENTS.md 按路径作用域生效，越靠近工作目录，优先级越高。

```
my-repo/
├── AGENTS.md              # 项目级：团队规范（底线）
├── frontend/
│   └── AGENTS.md          # 局部：前端专属约定（覆盖项目级冲突项）
└── backend/
    └── services/
        └── AGENTS.md      # 更局部：支付服务专属约定（优先级最高）
```

规则按"全局 → 项目 → 子目录 → 更深的子目录"逐级叠加，深层规则覆盖浅层的同名规则。这让团队既能统一底线，又允许局部灵活定制。

级联的实用性在于"分而治之"：一个大型仓库往往同时存在老代码与新架构、多个语言栈，把彼此冲突的约定写进同一份 AGENTS.md 必然打架。级联机制让你按目录切分责任边界——根目录管通用底线，`frontend/` 管前端约定，`legacy/` 管老代码的保守策略，互不干扰、各管一摊。

::: tip 先约定再下钻
团队规则定"底线"（安全、规范），子目录规则做"差异"（模块专属），避免把所有细节都堆在根 AGENTS.md 里——否则层级就失去意义，所有目录都被一视同仁。
:::

## 三、编写有效规则

### 3.1 规则写什么

一份好的 AGENTS.md 建议包含六类内容：

| 内容类型 | 说明 | 示例 |
| --- | --- | --- |
| 仓库结构 | 告诉 Agent 代码在哪 | "前端在 `frontend/`，后端在 `backend/`" |
| 构建/测试/lint 命令 | 用对命令才能少走弯路 | "`npm run build` 构建，`npm test` 测试" |
| 工程约定 | 项目特有的写法 / 约束 | "组件统一用 TypeScript 编写" |
| PR 期望 | 提交流程与质量标准 | "PR 需附变更说明与测试" |
| 完成定义 | definition of done | "通过 lint、测试、无未解决 TODO" |
| do-not 规则 | 明确禁止的行为 | "不要提交 `node_modules/`，不要改锁定文件" |

### 3.2 可复制的 AGENTS.md 模板

```markdown
# AGENTS.md — 项目指令

## 仓库结构
- `frontend/`：Vue 3 + TypeScript 前端
- `backend/`：Node.js + Express 服务

## 构建与测试
- 构建：`npm run build`
- 测试：`npm run test`
- 类型检查：`npm run typecheck`

## 工程约定
- 新代码必须通过 `npm run typecheck`
- 组件遵循目录内 README 的命名规范

## PR 期望
- 每个 PR 附一句变更摘要和测试说明
- 大型改动请在 PR 描述中给出分步说明

## 完成定义（Definition of Done）
- lint、类型检查、测试全部通过
- 无未解决 TODO
- 变更已覆盖测试

## Do-not
- 不要提交 `node_modules/` 与 `.env`
- 不要直接修改 `package-lock.json`，除非变更了依赖
```

### 3.3 保持简短

AGENTS.md 不是文档站，Agent 每次会话都读，篇幅越长、重点越容易被稀释。**核心规则写满一屏即可**；深度的指南放 `references/`，在 AGENTS.md 里指个路就行。

::: warning 别把 AGENTS.md 写成 wiki
如果 AGENTS.md 超过几页，说明把"知识文档"误当"指令文件"了。规则要的是高信噪比、可直接执行的指令，不是背景介绍。
:::

## 四、规则的加载时机与作用域

### 4.1 路径作用域

规则按**路径作用域**生效：你在哪个目录工作，就加载哪一层规则。例如工作目录从 `backend/services/` 开始时，会依次叠加"全局 → 项目 → `backend/` → `backend/services/`"四层规则。

### 4.2 会话开始自动加载

AGENTS.md 在**会话开始时自动加载**，无需手动引用。这也是它与普通文档的关键区别——文档要人主动去看，规则是"开工前自动上桌"，天然保证 Agent 每次都知道规矩。

加载是"拉起快照"而非"实时轮询"：规则在你启动会话的那一刻进入上下文，之后的对话都在这份规则的约束下进行。因此改完 AGENTS.md，需要**重启会话**才能让新规则生效；如果你改完规则发现行为没变，先检查是不是忘了重启。

另外要注意，规则与 config.toml 的加载时机一致——都是会话启动时读取配置。若在会话中途改了 `approval_policy` 等行为配置，同样需要重启才生效。

### 4.3 把已验证的 prompt 编码进 AGENTS.md

prompt 一旦验证有效，就该编码进 AGENTS.md，避免每条 prompt 重复。AGENTS.md 本质上是"已验证 prompt 的持久层"：把一次有效的工作流固化下来，Agent 就持续按这套经过验证的方式工作。用 `/init` 命令可快速生成 AGENTS.md 脚手架，再按模板填充。

::: tip 善用 /init
`/init` 会为项目生成 AGENTS.md 脚手架，自动探测仓库结构、构建命令等基础信息，省去手写开头，是搭建规则体系的捷径。
:::

## 五、实战案例

### 5.1 案例一：团队规则集（仓库根 AGENTS.md）

团队在仓库根放一份统一 AGENTS.md 定基线：构建命令、测试门槛、PR 期望、do-not 规则（示例见 3.2 模板）。所有成员在同一套规矩下协作，评审成本大幅下降；新成员进入项目，规则随仓库自动生效，无需口头培训。

### 5.2 案例二：个人全局规则（~/.codex/AGENTS.md）

个人在 `~/.codex/AGENTS.md` 放"跨项目通用"的规则，每个会话都会加载：

```markdown
# 全局个人规则

## 通用约定
- 代码保持简洁，优先可读性
- 改动先跑对应测试，再告知结果
- 提交信息用中文描述要点

## Do-not
- 不要删除用户没有明确要求删除的代码
- 涉及删除 / 覆盖文件前，先确认再执行
```

这份规则对所有项目生效，是你个人的"行为底线"。

### 5.3 案例三：子目录局部规则

对仓库里某个特殊模块（如 legacy 代码、特定服务），在子目录放局部 AGENTS.md，只约束该目录：

```markdown
# backend/services 局部规则
- 该服务保持 Node 14 兼容，不要引入新语法
- 改动需同步更新 docs/api.md
```

只有进入该目录工作时才生效，不影响其他模块——既满足局部需求，又不污染全局。

## 六、最佳实践与常见问题

### 6.1 最佳实践

- **具体可执行**：规则要具体到命令和标准，少用"注意质量"这类空话；
- **命令必须真实**：写进 AGENTS.md 的命令必须能跑通，写错了会让 Agent 反复试错；
- **遵循跨工具标准**：AGENTS.md 是 agentsmd.io 的跨工具标准，Claude Code、Cursor、Windsurf 也读它——一份规则，多工具受益；
- **定期收敛**：把每次 prompt 里反复出现的内容迁入 AGENTS.md，Prompt 只留一次性需求。

### 6.2 常见问题排查

| 问题 | 排查步骤 |
| --- | --- |
| 规则好像没生效 | 确认文件位置与作用域（全局 / 项目 / 子目录）；确认会话在正确的工作目录 |
| 子目录规则被覆盖 | 检查更深层是否定义了同名规则；深层优先级更高 |
| 规则太长 Agent 抓不住重点 | 精简到一屏，长指南移入 `references/` |
| 想把持久规则写进 config.toml | 拆开：确定性行为进 config.toml，项目知识进 AGENTS.md |

::: warning 别把所有东西塞进 config.toml
config.toml 管"开关"，AGENTS.md 管"规矩"。把工程约定写进 config.toml 会让配置臃肿且不可随仓库移植；反过来，把模型名、审批策略写进 AGENTS.md 也不合适——它们不是给模型读的指令。
:::

## 七、总结

Rules 用 AGENTS.md 承载持久指令，按"全局 → 项目 → 子目录"嵌套级联、越近优先级越高，再配合 config.toml 的确定性行为配置，构成一套完整的规则体系。把已验证的 prompt 沉淀成规则，是让 Agent 稳定、可预期、少犯错的最高性价比手段。结合本教程的 AGENTS.md、Skills、Plugins 等章节，你就能构建一套完整的 Codex 定制体系。
